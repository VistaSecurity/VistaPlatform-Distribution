    Vista Platform 5.4.0 — full list of changes¶

    Covers 5.4.0 through its release candidates. The release summary — what 5.4.0 changes, what to do before upgrading, and how to verify the signatures — is in the CHANGELOG published with that release. This page is the complete, per-change record behind it.

    5.4.0 makes the inventory measure one device on many networks, keeps it current, and shows what changed. A device's own report now decides its class, role and routed networks; a new device or cloud account is collected as soon as it is added and then re-observed on a schedule; and Discovery shows what was fixed, what was checked and what changed. The Linux agents move to the vista-* names, and every system has a service installer for each agent.

    • Daily re-observation for every collector. One re-observation interval on Settings → Discovery → Active Scanning (daily by default, a Tenant Admin may shorten it) now drives the automatic scan, a new re-handshake of the known endpoints serving discovered certificates, and a default schedule every device with credentials and every cloud integration gets on Discovery → Scheduled Scans (marked Default; pause or delete it to opt out). Host inventory stays off. The unused scan_interval (sensor configuration) and revalidation_schedule (lifecycle policy) API fields are removed.

    Added¶

    • Adding a source starts its first collection. A cloud integration is listed as soon as it is connected and enabled, instead of waiting for its default schedule or a press of Discover; switching one on, or correcting the credentials of one never listed successfully, does the same. A device added through a device agent is interrogated at once by that agent, and a device held for review when it is approved. Both already happened for a device the platform reaches directly.
    • One device, many networks. A router, firewall or layer-3 switch that a sensor hears on several networks is one record: when the device itself reports an interface list whose hardware addresses cover both records, they are merged by rule (listed under Discovery → Review → Merged automatically with the evidence), regardless of network. An LLDP chassis id written as a MAC now identifies the device, not the port that sent the frame. A gateway's WAN address is never its primary address or name while it has an address on one of your networks, and an existing record is repaired on its next sighting. Keep separate from… (asset page → More actions) records that two records are different devices, and Allow merging again… undoes it.
    • Who routes each network, from any vendor. The device's own addresses, SNMP IP forwarding, DHCP (the router a lease names), FHRP virtual addresses, a host's default gateway and the device's class are recorded as gateway evidence for the networks they concern; a corroborated device is linked as the network's gateway, a contested network opens a Proposed gateway question in Discovery → Review → Approvals, and IP forwarding alone only asks. The Networks lens has a Gateway column; a prefix's panel has Set gateway… (a declared gateway is never replaced by measurement) and Clear.
    • Class and role from the device itself. The class a collector reads from the device (router, firewall, switch, wireless controller) now reaches an asset that is still Unknown host, and a different measured class opens a question under Approvals → Classes; Confirm class on the asset page declares the current one. A switch that forwards IP is a layer-3 switch. The asset Overview shows Roles badges (gateway for N networks, layer-3 switch, VPN endpoint, upstream next hop, device role) derived from evidence.
    • Upstream / ISP edge. Each collector reads only the device's default route (one next hop, never a routing table). A public next hop becomes an external upstream asset joined to the router by a connects_to edge and drawn as an Upstream node on the map; a next hop inside one of your networks is gateway evidence for it. A WAN interface's public network is never learned as one of your networks. If you own public address space, declare those networks.
    • A router's VPN is the router. Remote-user VPN (SSL-VPN, IKE dial-up, WireGuard) is a service endpoint on the router, with its crypto posture, not a second asset or a tunnel; site-to-site tunnels keep their terminations and get the WAN port's address as outside IP; several tunnels may terminate on one WAN port. Leftover VPN records from earlier releases fold into the router on its next interrogation unless a person edited them.
    • The platform tells you when something gets better. Two new notifications, Finding resolved and Asset risk dropped, go to the default activity feed when a finding stops being detected or an asset's risk band falls. Two new alerts, Asset not seen (an asset crossed the stale threshold) and Auto scan refused (the last automatic sweep left assets unscanned for want of a sensor or of scan consent), open and resolve like any other. A routing rule can now name one alert type.
    • See what was fixed, what was checked and what changed. Findings lists (Risk & Compliance → Findings and an asset's Findings tab) can show Resolved, All or Fixed in the last 7 days findings beside the Active ones, and a finding's inspector has a Timeline (last checked, resolved, every transition). Assets, endpoints and crypto configurations show Last probed / Last complete observation beside Last seen. Endpoint, crypto configuration and certificate changes a scan measured (a port closed, a cipher no longer offered, a risk band moved, a certificate expired) are recorded in the change log, and Discovery → Activity → Feed lists discoveries, changes, findings and scans in one place.
    • Re-check a finding. The finding inspector and a ticket linked to a finding have a Re-check button: it scans the finding's asset and reports in place whether the finding is still detected, and when it cleared.
    • System Health → Inventory currency. The admin console's System Health page has a panel that says whether the loops keeping tenant inventories current are running: the last automatic-scan sweep, assets overdue for a rescan, the oldest unprocessed sensor observation, observations rejected after their retries, and the last finding-producer pass, each amber or red against a stated threshold and Unknown (never green) when its service does not answer. inventory-service and discovery-processor-service serve the readings on GET /metrics (discovery-processor's was a stub).

    Changed¶

    • A denied asset is the only record of a denial. Denying a device keeps it out for as long as the denied asset exists, however it is seen again. Deleting a denied asset now forgets the denial on every path: the device is offered again in Approvals the next time a sensor sees it, as it already was when an agent re-added it. Before, a hidden name-address-port fingerprint kept sensors from re-discovering a denied device after its asset was deleted, could not be seen or undone, and also hid any other device that took the same name and address. Devices that were denied and then deleted on an earlier release, and are still on the network, will appear in Approvals once.

    • PQC capability is a badge, and quantum vulnerability leaves the risk score. A crypto configuration earns a PQC badge when each role it has (key exchange, authentication including the certificate it presents, symmetric cipher, hash) can do post-quantum cryptography by the algorithm catalogue, hybrids such as X25519MLKEM768 and sntrup761x25519 included. An asset earns it only when every live configuration has it. The chip shows on configuration and asset rows, the asset's Status block and Services & Endpoints, and the configuration drawer says why role by role. The Assets lens has a PQC capable facet (pqc.capable:true), the Configuration lenses a PQC capable filter, and Dashboard → PQC two tiles, PQC-capable assets and services. The Vulnerable to quantum attack finding is now informational and no longer feeds asset risk, so classical cryptography alone no longer holds an asset at Medium. The Post-Quantum Readiness framework is unchanged. /pqc/progress and /pqc/summary add badged_configurations, badged_assets and assets_with_configurations. The catalogue now gives the SSH ciphers and MACs a NIST quantum security category.

    • Tenant health sees posture. The tenant health index (admin console → Support → Tenant Health) now weighs inventory posture — the tenant's framework score and its open findings by severity — at 40 of 100 points, beside performance (25), account security (20) and business activity (15); an open critical finding lowers it. The account-hygiene number (unverified e-mail addresses, old passwords) is no longer called a compliance score: the API field is account_hygiene_score, and compliance_score is a deprecated alias for one release.
    • A resolved alert's notice travels the route the alert took. "Resolved: …" is delivered at the severity the alert reached, not at informational, so a rule for high and critical alerts now hears that they cleared.

    Fixed¶

    • An AWS certificate survives its next listing. A certificate known only by serial and issuer (ACM never returns the certificate body) was stored on the first listing and then failed the fingerprint constraint on every later one, so its links and findings were lost and retried forever. Later listings now find the same row.
    • The install steps match the published installers on every system. Discovery → Sensors & Agents → Register now uses the installer for each system an agents release publishes one for: the macOS installers and the Windows device agent installer as well, in place of a foreground run or a device-agent.exe console run. The steps take the sensor's and the device agent's CA fingerprint on every system, no longer rename the binary, and print no installer a release does not carry. The Core guides say the same, name the Linux services vista-sensor and vista-device-agent, and explain that re-running the installer moves an install with the old crypto-* names in place, without enrolling again.
    • A commercial release needs qualified agents. release-customer.yml only warned when no public agents were qualified for the version, so a release could ship with the in-product agent download answering 404. It now refuses before anything is published, as the Core release already did.
    • Test Connection starts the first listing. A cloud integration that reached "connected" without being added through the app (restored from a backup, upgraded, or fixed after its first listing failed) was only listed when its daily schedule fired. A passing Test Connection now queues the first listing, and only if none has been queued or completed; a failed test queues nothing.
    • A removed device or deleted cloud integration stops being scanned. Removing a device used to leave its schedule behind, which then created a job every day that could only fail with "device not found"; deleting an integration did the same. The schedules are now removed with their target, and a schedule whose target is already gone (from earlier removals) retires itself the next time it falls due instead of failing forever. A device added again gets a fresh default schedule; a default schedule you deleted yourself is still never recreated.
    • A managed device keeps its identity, and an interrogation says what it could not file. The rule that lets a DHCP address follow a MAC could take the address off a device you had put credentials on, or empty any live record, when a second record of the same device turned up by MAC. That record could then never be matched again, and every interrogation of it dropped the serial and the whole network while the job read as fully materialized. The address now stays and the two records go to Discovery → Approvals as a merge proposal, which the same-device rule merges automatically when the tenant allows it. An interrogation of a record left empty by an earlier release gives it the identity the device reports, or raises the proposal, on its next run. A run that cannot file something now says so on the job, with fully_materialized: false, on both the agent and the in-cluster executors. Records already emptied are not repaired until their next interrogation, and an unmanaged emptied record has no such run: use Approvals or delete it.
    • The class a device reports refines a general class without asking. A Network device the device's own collector reads as a router or a firewall takes that class on its next interrogation, and the question already open under Approvals → Classes closes. A sibling class, an imported class, a class a person chose or rejected, and a low-confidence hint still ask.

    • The learned classifier no longer questions a class a collector decided. A Linux server with ports 22 and 80 open was asked about being an access point. A model answer against a measured, rule-derived or imported class is no longer raised; a pending one stays until it is decided.

    • Reinstalling a sensor or a device agent on the same host works. After the old installation was deleted, every report of the new one waited in Approvals as an identity conflict (no host inventory applied, the sensor's self-observation not attached). The new installation's first report now retires the deleted installation's id from the host's asset, with a history entry, and is applied; a host left in that state by an earlier delete recovers on its next report (on a tenant with identity admission off, where the conflict also made a second, pending record of the host, that record still has to be merged in Approvals). A reinstall whose old installation was not deleted is still a question in Approvals: delete the old one.

    • Re-adding a device whose asset was deleted works. Adding it again through an agent, a sensor that still saw it, a new device on its old address and a manual create with its serial all failed with "identified, but it couldn't be recorded" (or a failed import). A deleted asset no longer identifies anything: the device becomes a new asset (in Approvals, or straight into the inventory where the network auto-approves) that takes over its identifiers, with history on both records. Restore is refused once that has happened, and says which asset the device is now. To stop tracking a device, Deny it. inventory-service now also logs why an internal service call failed.
    • Deleting an asset, a module bay or a whole tenant no longer reads every interface or module once per deleted row. The interface and module tables had only a partial index by parent, which the delete cascade could not use, so purging a tenant with 50,000 assets and 500,000 interfaces ran past the ten-minute purge limit; it now takes under three minutes. The upgrade adds two indexes (idx_interfaces_tenant_asset, idx_modules_tenant_module_bay).
    • Tracing a patch-panel port (front or rear), and working out which cable paths to redraw after a cable changes, no longer read every stored path of the tenant. The index meant for that lookup could not be used under tenant isolation, so both grew with the number of cables (about 155 ms per trace at 100,000 cables); they are now a direct lookup. The upgrade adds a table (cable_path_nodes), fills it from the existing paths, and drops the unused index.
    • Tracing a patch-panel port (front or rear) on a tenant with many cables no longer tests every stored path in index order; at 100,000 cables the trace went from about 155 ms to about 45 ms.
    • FortiOS singleton endpoints (vpn.ssl/settings) are decoded; SSL-VPN settings were silently skipped with a parse warning.
    • Interface addresses in CIDR form from the Fortinet, Cisco, Palo Alto and F5 collectors are read by the gateway paths (they were dropped silently, so only SNMP and UniFi ever produced gateway evidence).
    • A router's VPN is the router. A VPN service an interrogated device reports (a FortiGate SSL-VPN portal or IKE dial-up, a UniFi WireGuard, OpenVPN or L2TP server) is a crypto configuration of that device on an endpoint at the address it answers on, never a second asset beside it; an asset an earlier version created that way is merged into the router on the next interrogation (listed under Merged automatically). Remote-access VPN is no longer filed as a tunnel, and several tunnels over one WAN port each terminate on their own tunnel interface with the WAN port's address as their outside IP.

    • The PQC badge requires post-quantum authentication. A TLS 1.3 service with a hybrid key exchange and a classical certificate no longer earns the badge: authentication must be assessed and post-quantum, and when no certificate or signature could be read the configuration drawer says authentication is not assessed. Certificate signatures spelled the way the x509 library spells them (SHA256-RSA) are now matched to the catalogue. A catalogue change, such as an upgrade's seed, now reaches the badge within minutes rather than at the next producer pass.

    • A late or replayed observation no longer makes the inventory older. A certificate verification, an external connection or an interface observation that arrives after a newer one can no longer move "last verified" / "last seen" backwards or replace what the newer one measured, and a sensor that resends a discovery batch no longer stores it twice.

    • Automatic scanning records every host it did not scan. Each asset now says what the automatic scan last did with it — scanned, unreachable (since when), refused (why), held back (the pass was full, a sensor was busy or offline, the rate limit), or scan in progress — and a host is recorded as scanned only when the scan actually reached it, not when it was queued. A scan whose sensor stopped before reaching a host hands it back as due. Settings → Active Scanning no longer says "Every eligible host was scanned" over a pass that held hosts back; it says what happened, with a link to each list. New built-in views (Not probed recently, Refused or unreachable, Scan held back) and two Dashboard → Assets tiles. Hosts that cannot be scanned this pass no longer use up the pass's limit, and a sensor with a full queue is not sent more work to refuse.

    • A hardened service's crypto risk now drops on its next scan. When a server stops offering a weak algorithm (an SSH MAC, a cipher in a configured TLS cipher string, a VPN proposal), the next complete observation removes it from the crypto configuration, the configuration is re-scored from what the server still offers, and the weak-configuration finding resolves instead of being held open. Partial observations (a passive banner, a single negotiated TLS suite) change nothing.

    • What a scan no longer finds is retired. When an active scan negotiates something new on a port (TLS 1.0 turned off, a different cipher suite), the configuration an earlier scan recorded is retired from Inventory, risk and findings instead of being judged for ever (a handshake a sensor saw a client make is kept, unless the scan finds the server now refuses its TLS version — so TLS 1.0 turned off clears it); a superseded configuration still opens by id from a resolved finding or ticket; a renewed certificate stops being judged once no port serves it; and a port that refuses the connection on two consecutive scans of a host that answers is closed and its findings resolve. A passive sighting never retires or revives anything. See Active scanning.
