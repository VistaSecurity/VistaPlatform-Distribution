    Vista Platform 6.1.0 — full list of changes¶

    Released 2026-11-24. The release summary — what 6.1.0 changes, what to do before upgrading, and how to verify the signatures — is in the CHANGELOG published with that release. This page is the complete, per-change record behind it.

    Upgrading¶

    6.1.0 upgrades from 6.0.x; a 5.4.x install upgrades to 6.0.x first. An install on 5.0, 5.1, 5.2 or 5.3 takes the latest 5.4.x, then 6.0.x, then 6.1.0; the 6.0.0 upgrade notes describe those earlier steps and the commercial model that came with 6.0.0.

    Back up the database first, as before every upgrade: Maintenance → Backups → Create backup in the admin console, or pg_dump. The chart's upgrade notes print the pg_dump command for the bundled PostgreSQL.

    • The schema change is additive. 6.1.0 adds three tables for the AI assistant: its questions while they run, the encrypted placeholder maps that go with them, and Assistant notes. The chart's schema-migration Job (or the compose file's db-migrate service) creates them as usual. It also adds one column to the device job table, which records whether a stored interrogation result has been processed. No existing column or row is changed, and nothing is moved. The seed adds the AI Assistant capability to the entitlement catalogue and the edition plans, the assistant_notes.manage permission (held by Tenant Administrator), and an algorithm catalogue row for RSA signatures whose hash was not observed (see Fixed).
    • One column on IP addresses, and some addresses move to a device's own VRF. 6.1.0 adds a placement column to the IP address table. No row is changed by the migration. The first interrogation of a device after the upgrade re-reads where each of its configured addresses belongs: an address that was filed in one of your networks only because its range matched, on a network that has another device as its gateway, moves to a VRF of the device's own and shows Network not confirmed. The address keeps its record and its change history, and you can move it back with Same network. See Networks that reuse an address range.
    • On Vista Platform Core, Ask is locked. In 6.0 a model provider that the platform administrator connected answered Ask in every edition. From 6.1.0 asking in words, conversation history and action cards are the paid AI Assistant capability: Core shows a lock card in their place and makes no request to a model. Inventory search, filters and saved queries are unchanged. See Editions.
    • NetBox sync reads NetBox's version first. Every sync run and Test read GET /api/status/ on your NetBox with the connection's token. If a reverse proxy or web application firewall blocks that path, the run stops before it reads or writes anything and says what /api/status/ answered; allow the path through and run again.
    • compliance-engine's /metrics needs a signed request. It now answers only signed service-to-service calls; an unsigned scrape gets 401. /metrics/health stays open for probes. If you scrape compliance-engine's /metrics with your own Prometheus, expect that target to go down.
    • Some audit reads need audit.read. See Changed. A custom role that reads job execution logs, alert rules, compliance reports or the audit analytics through the API needs that permission.
    • Removed API routes. If you call any route listed under Removed, change the caller before you upgrade.

    Agents¶

    Sensors and device agents are not built or shipped by the platform. Each 6.1.0 install offers the agents release named by its signed compatibility record, shown in Discovery → Sensors & Agents → Register sensor or agent as Qualified by record …; the files are at https://github.com/VistaSecurity/VistaPlatform-Agents/releases. An agent or sensor that is behind that release shows Update available in its detail drawer; Show upgrade steps prints the commands.

    Changes¶

    Added¶

    • A tenant's recent activity in the admin console. Tenants → open a tenant → Activity lists the tenant's latest 25 audit entries (action, target, actor, category, time, and a Failed marker) for platform admins who hold platform.audit. Open in Activity Log sets the console's scope to that tenant and opens Security → Activity Log for search, filters, entry detail and export.
    • Third-party licences are enforced, and each release has an evidence package. Every Go module, npm package and image is held to a written licence policy on each change and again before a release is published. The NOTICE in each image also names the MPL-2.0 modules inside the bundled helm and cosign programs, the embedded font in the web server, and the position on the Alpine base image's GPL packages. On request we supply a per-release package with a complete SBOM for every image, the licence report and a vulnerability scan.
    • Networks that reuse an address range. A device's configured address is filed in one of your networks only when something shows the device is on it (it reported the network, it is the network's gateway, it was reached at that address, another collector saw it there, or nothing contradicts it). Otherwise the address stays with the device in a VRF of the device's own, with its prefix, and identifies nothing on your network. The asset's IP Addresses tab shows Network not confirmed and a prefix's panel lists such devices under Also configured on; both offer Same network and Separate network to roles that manage IPAM. A firewall's unused factory-default inside network no longer takes an address from, or is offered as a merge with, a different device on your network of the same range. See Networks that reuse an address range.
    • Tenant operational health in the admin console. A tenant's health now means "is this tenant's platform working", not a score. Support → Tenant Health lists every tenant's status — Healthy, Degraded, Down or Unknown — sorted Down first, with the number of failing checks, the open alert and the time of the last check. Mission Control lists tenants that are Degraded or Down with their first failing check, and on MSP the Tenants list and the tenant drawer show the same status.
    • Named checks. The drawer lists Sensors reporting, Discovery agents reporting, Collections succeeding, Schedules running, Plan limits, Integration syncs, Notification delivery, Rate limiting and Ingest succeeding, each with its result, its evidence and when it was measured. A check with nothing to measure (no enrolled sensors, say) reads Not applicable and never counts as Down.
    • Status history shows the transitions and the time spent in each status over 30 days. Earlier health-index history is not converted into statuses.
    • Adoption is its own section: users who signed in over 7 and 30 days, the last sign-in, API calls over 30 days, assets used against the limit and seats used against the limit. A figure that could not be read says so; it is never shown as zero.
    • Alerts. The tenant health degraded alert names the failing checks and takes the severity of the worst one (a Down tenant is critical). It updates when the failing set changes, resolves when the tenant is Healthy again, and does not fire for a tenant that is Unknown or whose checks are all not applicable. A new platform alert, tenant health evaluator stale, fires once when the health evaluation has not run for 15 minutes or when tenants that could be measured stay Unknown for an hour.
    • Compliance posture and tenant findings are no longer part of tenant health; tenants see them in Risk & Compliance. See the Platform Admin Guide.
    • Inventory explains why an asset was or was not scanned. Automatic scans and the scans you start share one set of reasons, and every place that shows a scan uses it:
    • The asset page and the asset drawer show the asset's latest scan outcome: scanned (a service found, or the host answered with none), in progress, not authorized (the network is not registered, the address is excluded, or the source that imported the asset has no active-scan consent), no eligible collector, the observing sensor offline with no other sensor covering the network, deferred (the scan pass was full or the collector busy), rate limited, unreachable, or attempted and failed. While a replacement sensor runs a scan for an offline one, both are named; once the sensor is back, the offline explanation clears. Each reason links to what fixes it: Manage sensors, Review active scanning, Review source consent or Open discovery jobs.
    • The asset lenses gain a Scan outcome column (shown by default) and a Scan state filter in the filter rail: In progress, Deferred, Rate limited, Refused, Unreachable and Scanned.
    • Manual and bulk scans that skip an asset say why in the same words.
    • Possible same device. In Discovery → Review → Observations, unresolved observations of one personally named phone or tablet seen on several networks are grouped under a Possible same device banner that counts the observations, networks and inventory items involved. The banner changes nothing: each observation stays separate, keeps its own row and is confirmed or dismissed on its own. Factory names such as iphone are not grouped.
    • Approve many pending networks and VLANs at once. On Inventory → Networks & IPAM and Inventory → VLANs, each pending (discovered) prefix or VLAN has a checkbox, and Approve selected approves them all, each the way its own Approve button does; the bar then says how many were approved and how many were not. Only pending objects can be selected, and only by a role that manages IPAM.

    Changed¶

    • The Quantum readiness card is about key exchange. The Dashboard's Quantum readiness widget used to draw every crypto configuration as quantum-ready, awaiting migration or not yet assessed. A configuration was ready only when nothing classical was left in it, so one RSA or ECDSA certificate put a server that already negotiates a post-quantum key exchange under "awaiting migration", and the widget read 0 ready for nearly everyone. It now reads N of M connections protected against future decryption (the configurations with a post-quantum or hybrid key exchange), with the count that can be upgraded now and the count not yet checked; each count opens exactly those configurations in the Configuration lens, where a chip names the filter and clears it. Classical certificates are one sentence, since post-quantum certificates are not generally available. The new Quantum readiness breakdown widget, which the PQC template now places, shows key exchange and authentication separately, each as post-quantum, classical or not seen, with the reason anything was not seen. The four categories are unchanged and still feed the PQC ready figures on the posture widgets and Remediation → Progress. For integrators: GET /pqc/progress carries by_role, and GET /crypto-configurations accepts pqc_key_exchange=capable|not_capable|not_seen. See Dashboard → Post-quantum readiness.

    • The AI assistant is a paid capability, separate from connecting your own provider. Asking in words, conversation history and action cards are the AI Assistant capability, included from Starter and in the trial; Core keeps inventory search and shows a lock card for Ask. Connecting an organization's own model provider stays the separate Own AI Model Provider capability: an organization with the assistant but not its own provider uses the one the platform administrator connected. Turning the assistant off for an organization still refuses with its own message, not the lock card. Editions lists both.

    • Installing a sensor or device agent on Windows is easier to follow. The Windows steps in Register sensor or agent no longer need cosign: they always check each download's SHA-256 against the value the platform build was qualified with, and verify the Sigstore signatures too when cosign.exe is installed. They check for an administrator PowerShell window (and, for a sensor, Npcap) before downloading anything and work in their own folder, and the dialog says how to open PowerShell and paste them. Or do it by hand under each Windows block lists the files to download and the installer or guided-setup command to run. Linux and macOS steps are unchanged and still need cosign. Windows binaries have no Authenticode signature and macOS binaries are not notarized.
    • Gateways and kept-separate records carry their context. A gateway proposal in Discovery → Review → Approvals shows the network's VLAN and site; the Gateway column of Inventory → Networks & IPAM names the gateway device and address from the prefix itself, without a lookup per row; and Allow merging again… on an asset lists only the records it is actually kept separate from.
    • Phone and tablet names stay put. A factory default name such as iphone ranks below a personalised host name, and two names of equal quality no longer replace each other on every sighting, so a managed phone's name stops flapping. Names you declared still win, and a phone seen on two networks is never merged on its name alone.
    • Audit reads need audit.read. In audit-service, job execution logs, alert rules, compliance reports (summary, retention check, templates and generate) and the audit analytics required only a signed-in user; they now require audit.read, as every other activity-log read does. Tenant Administrator, Security Administrator and Viewer hold it; Billing Admin, API User and custom roles without it no longer read these routes. Nothing in either console called them.
    • compliance-engine's /metrics answers only signed service calls. /metrics/health stays open, like /health.
    • An admin template applied to a tenant's custom policy checks the tenant's plan. Applying a measurement template to a tenant's Custom Policy from the admin console now requires that tenant to have Custom Policies, and answers 402 otherwise instead of writing the rule.
    • Copy buttons say when the copy failed. The sensor install command, the registration code, the Platform CA fingerprint, the MCP URL, a new API token, a certificate's PEM in a finding and the admin console's invitation and reset links show a message when the clipboard refuses, instead of doing nothing. Copying a certificate's PEM now also works over plain HTTP.
    • Settings is its own view. Choose Settings (or My Profile) from the profile-chip menu and the left rail swaps to the settings navigation, with Back to console at its top returning you to the page you came from; the rail no longer has a Settings button of its own, and Settings no longer slides up as a drawer over the console's navigation. /settings opens a Settings home with one card for each settings page you can open.
    • An Assistant entry in the left rail. A sixth entry, Assistant, follows the five sections for every user. Where the assistant cannot be used (Vista Platform Core, no model provider connected, the assistant switched off for your organization, or no permission to read assets) it shows a lock and opens a page that names the reason.

    • An interrogation result is stored first and processed afterwards. A device agent is answered as soon as its result is stored, whatever the size of the result, and a worker then writes it into the inventory; what an interrogation run by the platform itself observed, and a host inventory an agent collected as a job, go the same way. The device job reads Completed when the result is stored; its detail in Discovery says whether the result is waiting, being processed, processed, or stopped part-way, and a result that stopped part-way is continued automatically from where it stopped (up to five attempts) instead of waiting for the next run of the device. A large result is written a part at a time with no limit on the whole, the tenant's other collections take their turn between parts, and the job detail counts the devices and connections written so far. For integrators: GET /jobs/{id}/results carries processing_state and processing_progress.

    • Bundled components and datastore images are refreshed. The helm and cosign binaries inside maintenance-service and the Caddy server in the two UI images are rebuilt on newer modules (golang.org/x/crypto v0.59.0 for helm and Caddy, OpenTelemetry v1.47.0 for cosign). The chart's default Valkey image is valkey/valkey:8.1.12-alpine and its smoke-test image curlimages/curl:8.23.0; the compose files use PostgreSQL 17.12, Valkey 8.1.12 and NATS 2.14.10. Every image is rebuilt on the current Alpine 3.24 packages, which brings OpenSSL 3.5.9-r1.

    Removed¶

    These routes had no caller in either console. If you call one directly, use the replacement named.

    • POST /api/v1/auth-service/auth/initiate, /auth/authenticate and /auth/complete: an email-first sign-in dispatcher whose password step returned tokens in the response body instead of setting cookies. Sign in with POST /auth/methods, then POST /auth/login or single sign-on.
    • GET /api/v1/auth-service/auth/sso/providers: mounted without authentication, so it always answered an empty list. The sign-in screen discovers single sign-on through POST /auth/methods; Settings reads GET /tenant/sso/providers, which is unchanged.
    • POST /api/v1/auth-service/auth/sso/link: it wrote an identity-provider subject taken from the request body onto the caller's account, with no proof from the identity provider. A provider is linked when you first sign in with it. Signing in with single sign-on to an existing password account with the same email address is refused, with a message that says to keep using your existing sign-in method and ask your tenant administrator for help.
    • PUT /api/v1/admin-service/admin/tenants/{id}/billing: it reported a billing update as scheduled but only wrote a local placeholder row. Use POST …/billing/change-plan for a plan change.
    • POST /api/v1/compliance-engine/frameworks/licenses and PUT /api/v1/compliance-engine/frameworks/licenses/unlock: use POST /frameworks/subscribe, DELETE /frameworks/subscribe/{id} and PUT /frameworks/default. GET /frameworks/licenses is unchanged.
    • Drift detection is no longer listed in Settings → AI assistant. The row read Not yet built on every install: no AI capability implements it. The rule-based drift findings (a class new to a prefix, a port, protocol or certificate issuer new to a host) are unchanged and appear in Risk & Compliance → Findings. The page now lists only capabilities that exist, and its Where column names the Assistant drawer for Ask a question and Propose actions, and the platform operator's review for Catalogue enrichment.

    Fixed¶

    • The admin console showed "SSO disabled" for every tenant. The tenant list and drawer read a column nothing writes. They now follow the tenant's enabled identity providers, the same rule the tenant's own Settings page uses; a change can take up to 30 seconds to show in the list. The SSO tab says that the tenant's administrators manage the provider in their own Settings.
    • The PQC capable filter on the Configuration lenses did nothing. The list accepted pqc_capable and never applied it, so the PQC capable chip and the Dashboard's "PQC-capable services" tile opened every configuration. They now open only the badged ones.
    • Certificates recorded with a "with" spelling were not recognised. A signature recorded as SHA256WITHRSA, SHA256WithRSA or ECDSAWithSHA256, the form cloud APIs and some collectors report, did not match the algorithm catalogue's RSA and ECDSA rows. A service whose certificate carried only that spelling read "not assessed" for post-quantum readiness; it now reads classical.
    • A TLS service seen without its certificate no longer reads "signature RSA is not in the catalogue". The RSA in a suite such as TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256 could not be placed on one catalogue row, so the configuration's authentication was left unassessed. It now links to a new catalogue row for RSA signatures whose hash was not observed (code RSASSA: strong, classical, not quantum-resistant) and reads as classical. Existing configurations pick the link up the next time they are observed.
    • A discovered VLAN can be approved, and says where it came from. Inventory → VLANs and the VLAN page showed a Pending approval chip but no Approve button; both now have one (for roles that manage IPAM), show the VLAN's source and when it was first and last seen, and the VLAN page names the device each interface is on.
    • A device job says when its result was only partly processed. A large interrogation result whose processing reached its time limit left the job reading Completed with nothing to say part of the device was missing from the inventory. The job detail now says processing stopped before it finished; GET /jobs/{id}/results carries processing.incomplete and incomplete_reason.
    • A device agent no longer reports a completed job as failed. When the platform took longer than the agent's timeout to answer a result submission, the agent's retry was answered Job not found and the agent logged the job as failed, although the platform had stored the result and completed the job. A repeat submission from the same agent for a job it already finished is now acknowledged.

    • The hourly ingest counts behind tenant health are deleted after 30 days. Since 6.0.0 the clean-up had failed on every pass with a database error in the log, so the counts were kept indefinitely. No tenant data or health result was affected.

    • Quantum readiness no longer counts a service as ready on its key exchange alone. The Quantum readiness widget, the posture trend's readiness line and the map's per-device counts classified a TLS service that negotiates a hybrid post-quantum key exchange (X25519MLKEM768) as PQC-ready even when it presented an RSA or ECDSA certificate, because a TLS 1.3 cipher suite names no signature algorithm and the certificate was not read. The dashboard could show a ready share while the Inventory PQC capable filter matched nothing. The certificate now counts: a classical key or signature on it puts the service in Needs migration, and a service with a key exchange but nothing collected to authenticate it reads Not yet assessed. Expect the ready share to drop on tenants with TLS 1.3 services; the PQC badge and risk scores are unchanged.

    • One tenant's interface settings no longer leak into another's. Reading a tenant's UI configuration wrote that tenant's feature toggles into the shared defaults, so later responses for other tenants could carry them, and concurrent reads raced on them. Each read now starts from its own copy. The admin console's view of a tenant's UI configuration now also applies the platform defaults, as the tenant's own view does.
    • An action card that matches nothing cannot be approved. A reclassify or set-field card whose preview selected no assets offered Approve; it is now recorded as refused with no change to make.
    • Proposed actions stay with the question that proposed them. Reopening a kept conversation shows each action card's current state, and a running Discover Assets card picks up its progress again after a reload.
    • A trial-locked tenant is read-only everywhere, and ingestion keeps running. Writes through the web interface's newer API routes skipped the trial lock, while discovery imports, cloud key ingest and agent-host approval for a locked tenant were refused. Writes from a locked tenant are now refused on every route, and signed service calls pass. A tenant can reach this state only on a legacy trial plan carried over from 5.4.
    • The scan target "too large" dialog names the targets. A Discover Assets target too large to scan opened a dialog with empty target names.
    • Add circuit says where circuit providers come from. On a tenant with no circuit providers, the Add circuit dialog offered a required Circuit Provider list with nothing in it. It now names what is missing (a circuit provider, a circuit type or both) and links to Circuit Providers; the empty Circuits list points there too.
    • Device health answers honestly. The device health reads answer 404 for a device that does not exist instead of zeros, and the health timeline honours its interval.
    • Audit ingest rejects bad events clearly. An event with a missing or unknown category, user type or address is refused with 400 instead of 500, and an event that does not say whether it succeeded is recorded as a success, the column's own default, instead of a failure that could feed failure-count alerts.
    • Onboarding progress and EULA refusal answer correctly. Saving onboarding progress always failed with a server error, and refusing the EULA answered "Invalid request format" instead of saying the EULA must be accepted.
    • Accepting an invitation on a broken connection says so. The page stayed on "Checking your invitation…" for good; it now says the invitation could not be checked.
    • Measurement template routes return the right status. Deleting an unknown measurement template answers 404, and an unknown measurement type or a duplicate template code answers 400 or 409 instead of 500.
