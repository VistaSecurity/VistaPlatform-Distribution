    Vista Platform 6.0.0 — full list of changes¶

    Released 2026-11-12. Covers 6.0.0 through its release candidates. The release summary — what 6.0.0 changes, what to do before upgrading, and how to verify the signatures — is in the CHANGELOG published with that release. This page is the complete, per-change record behind it.

    Upgrading¶

    6.0.0 upgrades directly from 5.4.x only. The database schema was re-baselined for 6.0.0: the migration steps that carried a 5.0–5.3 database forward to the 5.4 shape are now part of the schema's definitions, so they no longer run on an existing database. 5.4.0 is the upgrade floor.

    • On 5.4.x: upgrade to 6.0.0 as usual. The chart's schema-migration Job (or the compose file's db-migrate service) applies the schema changes.
    • On 5.0, 5.1, 5.2 or 5.3: upgrade to the latest 5.4.x first, confirm it is running, then upgrade to 6.0.0. Going straight from an earlier release to 6.0.0 is not supported.
    • Before 5.0: there is no upgrade path (5.0.0 was a fresh install).

    Back up the database first, as before every upgrade: Maintenance → Backups → Create backup in the admin console, or pg_dump. The chart's upgrade notes print the pg_dump command for the bundled PostgreSQL. To see which release last wrote your schema before you start:

    SELECT app_version, chart_version, applied_at
  FROM schema_migration_status ORDER BY applied_at DESC LIMIT 1;

    If that names a release below 5.4.0, take the 5.4.x step first. You cannot skip it by accident: the schema apply refuses a database below 5.4.0 and tells you so. The migration (the chart's schema-migration Job, or the compose file's db-migrate) stops before changing anything, with an error that names the version it found and the 5.4.0 floor. On the Helm chart the pods of the release you are on keep serving while the new ones wait; restore nothing, just take the 5.4.x step, then upgrade to 6.0.0.

    The commercial model¶

    6.0.0 changes what Vista Platform is, and how you get it.

    • One image line. Every edition installs the same signed images and the same chart, released from one vX.Y.Z tag: docker.io/vistasecurity/<image> and oci://docker.io/vistasecurity/vistaplatform. Every release is mirrored to GitHub Container Registry (ghcr.io/vistasecurity) with the same digests and the same signatures, for installs that Docker Hub's anonymous pull limit refuses; the same cosign verify command checks either registry. A separate Core line, and core-vX.Y.Z tags, no longer exist. Without a licence an install runs as Core; a licence selects its edition.
    • Core is free of charge, with an allowance. Vista Platform Core is proprietary, free of charge, under the Vista Platform License, and has no time limit: 1 sensor, 1 device agent, 100 assets and 3 users. Past the allowance nothing is lost: an asset over it is held in Discovery → Review → Approvals, and sensors, device agents and invitations beyond it are refused. See Editions and allowances.
    • A 30-day trial of the whole product. A platform admin starts it on the admin console with their name, work email and company (a phone is optional), agreeing that Vista Security may contact them about the product in exchange for the free trial. Every capability is on, at Pro's capacity, for 30 days, one trial per installation. When it ends the install returns to the Core allowance and nothing is deleted. See Starting your trial.
    • Four paid editions: Starter, Pro, Enterprise and MSP. Every capability is in every paid edition; the editions differ in capacity, and Enterprise and MSP in tenants and contract terms. A licence can also raise or lower one allowance for one install. Prices are on the website, vistasecurity.io. The generated list of what is gated is on Editions.
    • A licensing service. Trials are issued, and licences are refreshed daily, by Vista Security's licensing service at licensing.vistasecurity.io. A running install never depends on it except to refresh; an install that cannot reach it starts the trial through a web form and pastes the token file it receives. A paid licence now has a 30-day grace after its expiry (extendable to 90 days while a renewal is in progress); a trial has none. See Installing and renewing a licence, which now covers every edition.
    • Usage reports from every licence. Every licensed install, a trial included, prepares a monthly usage report; Core reports nothing, and an Enterprise licence can opt out. See What is reported to Vista Security.
    • Allowance swaps. After a trial or a licence ends, a platform admin chooses which assets and which agents stay active: Promote and Demote in Approvals, Pause and Resume on Sensors & Agents.

    What a platform admin will notice of the removals¶

    • Plans & Pricing → Add-ons is gone. The placeholder page and its navigation row are removed, and the Entitlements catalogue no longer shows an Add-on column or an add-on price. An exception or an add-on is now part of the licence.
    • The Storage and PCAP-volume levers are gone from the catalogue and from every plan; nothing measured them.
    • Plans no longer show caps of their own. A plan's caps and capabilities are its entitlement composition; the copies a tier used to carry (maximum sensors, assets, users, retention) are removed from the tier and from the tiers API. The sample tiers (community, free, starter, pro, enterprise) are no longer seeded: an upgrade removes the ones no tenant uses and keeps the ones a tenant still does. A new tenant is placed on no tier unless the operator sets one.
    • The per-month usage history call is removed (GET /billing/usage/history): usage is counted live and reported through the usage report. The platform admin's tenant list shows API calls and shows storage as 0.

    Changes¶

    Added¶

    • The AI assistant asks about the thing in front of you, remembers, and proposes actions you approve. Ask (⌘K) grew in three steps, all behind the same gate: a connected model provider and your organization's AI assistant switched on. Every 6.0 image carries the model clients, so a provider the platform administrator connects serves every edition; an organization connecting its own provider is in the paid editions and the trial.
    • Ask about this asset. An Ask button on the asset page (and "Ask about this asset" on a finding) opens Ask pre-scoped to that asset; "how should I fix this?" lists its open findings by severity, each with a remediation plan drafted from the standard guidance and cited to the measurement it rests on. Plans need compliance.update; without it the findings are listed and the answer says so.
    • Conversations. With Keep conversation history on (Settings → AI assistant, off by default), every question, the query that ran, the rows and the cited answer are kept, follow-ups refine the previous query ("now only production"), and a History tab in the palette lists your conversations (a Tenant Administrator can list and delete everyone's, not read them). Retention follows the data retention cap with a 7-day floor.
    • Proposed actions. Ask in words for a change and the assistant answers with a plan of typed actions from a closed catalogue, one card per step: reclassify or set a field on every asset a query selects, approve or deny pending assets, open or update a ticket, or run a Discover Assets scan of a network you own. Each card shows the platform's own preview (the rows and count, the dry run, the drafted ticket as plain text), says whether it can be undone, and runs only when you click Approve, as you, under your own permissions; a later step may use an earlier step's result and still needs its approval. Reclassifications and field edits carry Undo. A Maximum assets per assistant action (default 200) and the owned-networks rule for scans bound what a card may offer; a target outside your networks is refused, never confirmed. The assistant has no credential of its own and never reaches the admin console, the audit trail, Settings or identity merges; the controls and the tests behind them are recorded for audit.
    • Cost controls. Per-capability effort levels and prompt caching on the Anthropic client, a Daily token budget per organization (0 = no limit; enforced through Redis, refused with a clear message when used up) and a Model dropdown filled from the provider after Test connection, on both AI settings pages.
    • Custom dashboards. The Dashboard section is now your own: boards you build from a catalogue of 29 widgets, in every edition and with no setting to turn on (#3029).
    • Edit a board. Click Edit to drag widgets, resize them within each widget's limits (a widget re-lays its content for the size it is given) and remove them with the ×; the Widgets drawer lists the catalogue grouped by the question each widget answers (What do I have? How exposed is it? Am I compliant? What do I do today? Where does it live?). Save keeps the layout and Cancel reverts. A window under 900 px wide shows boards read-only.
    • Many boards. New dashboard starts blank or from a template; the board menu renames a board, sets your default, resets it to its template and deletes it (your last board cannot be deleted). The Dashboard rail section (and ⌘K, as Dashboard: ) lists your boards in order, then New dashboard, and /dashboard opens your default. Your first visit creates your Overview board as the page looked before.
    • The five dashboards are templates. Overview, Assets, Compliance, PQC and Facilities are no longer fixed pages; each is a template, drawn from the same widgets (New dashboard → Start from). A bookmark to one of the old pages opens your default dashboard once and says where the page went.
    • One number per widget. Each card is a widget with its own data, loading, empty and error states: a failed read dims only that widget and reads "Couldn't load", never zero. A widget your role cannot read shows a lock card naming the permission it needs.
    • Stored per user. auth-service serves /api/v1/auth-service/dashboards (list, create, read, rename or re-lay, set default or move, delete) over a new user_dashboards table, and checks every saved layout against the widget catalogue in standards/dashboard-widgets.yaml.
    • Smaller changes to the pages: the Overview's four-stage lifecycle pipeline is gone (its sensors and ticket-workflow figures are the Sensors & agents and Remediation workflow widgets); the Assets, Compliance, PQC and Facilities content moved into widgets as listed under Changed.
    • The licensing service contract and its trial key. api/licensing/v1/licensing.openapi.yaml defines how an install starts its 30-day trial, refreshes its licence and sends its usage report to the Vista Security licensing service (licensing.vistasecurity.io), and every build now trusts the service's trial-only signing key, which can sign trial licences and nothing else. The key is generated on the licensing service and its private half never leaves it; trial licences signed by the key used during the early 6.0 release candidates do not verify on 6.0.0.
    • Custom Policies are evaluated (Starter, Pro, Enterprise and the trial). A tenant-authored policy is evaluated with the platform frameworks in the same pass: its controls raise findings and alerts, and each policy keeps a score with per-control status on Settings → Risk & Compliance → Custom Policies. Authoring is enabled again, and a change to a policy is re-evaluated shortly after it is saved (#1439).
    • SPDX and PDF downloads of a CBOM are in every paid edition. They follow the new cbom_formats capability, on in Starter, Pro, Enterprise and the trial and off in Core, decided per workspace when you download rather than by the build. On Core the Download menu shows them locked with the editions that include them, and the API answers 402 naming cbom_formats. They no longer follow cbom_signing; an MSP plan or tenant exception that set cbom_signing gets the same value for cbom_formats on upgrade.
    • Every release is mirrored to GitHub Container Registry. The images and the chart are also published at ghcr.io/vistasecurity/<image> and oci://ghcr.io/vistasecurity/vistaplatform, with the same digests, and signed and attested there by the same identity, so the same cosign verify command checks either registry. Docker Hub stays the default. When an anonymous Docker Hub pull is refused with toomanyrequests, install from GHCR with one more value, --set image.registry=ghcr.io (the chart's digest pins resolve unchanged), or point the compose file at ghcr.io/vistasecurity/. IMAGES.txt lists both registries.

    Changed¶

    • Algorithm catalogue and vendor registry refreshed for the release. The Algorithm Reference's migration guidance cites NIST IR 8547 as final (published October 2026; the 2030 deprecation and 2035 disallowance it set are unchanged), the hybrid TLS key exchanges cite RFC 10024 instead of the expired IETF draft, and the HQC rows say that FIPS 207 has no public draft yet instead of promising one in 2026. The IEEE OUI registry behind device-vendor resolution is refreshed to 10 November 2026 (about 250 new assignments). No rating, score or deprecation status changed.
    • Settings and detail views show names and values differently. The Trustworthy discovery policy (Settings → Active scanning), observation details in Discovery, the asset merge preview, the IP address drawer and the air-gapped licence instructions now show each name as a small muted label and each value in larger, bolder text, with identifiers in monospace and lists as chips.
    • The Infrastructure rail section is called Inventory again. The rail section holding the lenses (All assets, Sites & locations, Racks, Networks & IPAM, Certificates and the rest) and the workspace pages for the device catalog, organization, import and spares is labelled Inventory. Its address (/inventory) and every bookmark are unchanged; the command palette ("Inventory · Racks"), page headers and breadcrumbs, the inventory-hygiene finding guidance ("Open Inventory → Racks") and these docs follow it. "Infrastructure Assets", the name for the assets themselves, is unchanged.
    • Schema re-baselined; upgrade floor 5.4.0. schema.sql defines every table, constraint, index and trigger in its final 5.4 shape, and its upgrade block holds only the changes made since 5.4.0. A fresh install builds exactly the same database as before.
    • The posture trend shows more than one measurement. The chart on the Overview and Compliance dashboards and on Posture → Overview now plots the share of assets at high risk, the share that are unscored and the share of crypto configurations that are PQC ready, over bars of the monitored-asset count, with today's value and the change on each series, a scaled axis and a per-day readout. It draws measured days only, in a window that grows from five days to thirty; the flat "baseline" for a new tenant is gone. The daily snapshot now records the PQC counts and is refreshed hourly, so a restart can no longer skip a day. PQC history starts at the upgrade.
    • The Cryptographic Posture ring is drawn over the assets that carry crypto. Its slices are High, Medium, Low, Assessed clean and Not assessed; the centre is the number of assets the ring is made of, and the line beneath says how many monitored assets have no crypto observed (still a click away). Over a DCIM-shaped inventory the old ring, drawn over every asset, was mostly blank. The critical-findings count stays in Needs attention now.
    • Assets Monitored says three things. The headline count now carries a sparkline and the change since the trend's first reading, one bar splits the estate into Network devices, Hosts & compute, Cloud and Other (each a link into the inventory), and a single amber chip counts the assets waiting for approval. The nine DCIM counts it used to list (sites, AWS regions, racks, prefixes, VLANs, cloud accounts, clusters, certificates) are gone from the hero: sites are on the map beside it and the rest have their Inventory lenses.
    • The Overview is drawn as widgets on a grid. Every card is now a widget on an eight-column grid, laid out as before (the first step towards dashboards you build yourself, #3029). The Needs attention strip is five tiles — assets to approve, high-risk assets, critical findings, certificates expiring soon and stale assets — with sensors and agents and the ticket workflow beside them; the untrusted-certificate count moved into the certificate expiry outlook, and the PQC and not-assessed counts are in the quantum-readiness card and the posture ring. Assets Monitored splits the estate into Network devices, Hosts & compute, Cloud and Other instead of class groups. The lifecycle pipeline is gone; one failed read now dims only the widgets that use it instead of the whole page.
    • What moved when the four dashboards became templates. Nothing that was on the Assets, Compliance, PQC or Facilities pages was lost to the widgets: the Assets page's By environment, By business unit and By ownership panels are the Assets by class widget's switcher at four columns and wider, and its Unscored and No endpoints tiles are rows of Data quality at that width; the compliance finding workflow and the ticket mix are in Remediation workflow two rows high; the already-quantum-safe families and the VPN tunnels needing migration are a column of the PQC migration worklist at six columns and wider (the separate PQC Readiness score tile is gone — it was the quantum-readiness percentage drawn twice); the six Facilities tiles are the headlines of Rack space, Ports and addresses and Cabling backlog, whose site table now shows the five fullest sites instead of sorting by a clicked header. Scorecards and exposure lists show as many rows as fit their cell and say how many more there are.

    • A tenant has one health alert, and it is harsher. The tenant health degraded platform alert now opens at high when a tenant's health index is Poor and becomes critical at Failing (it was medium and high). Support → Tenant Health and the tenant drawer count that alert instead of a separate store tenant-health-service kept, which notified nobody. The board gains a Recommendations column (high- and critical-priority recommendations, which used to appear as an alert). The platform alerts API (GET /api/v1/compliance-engine/admin/alerts) accepts subject_id and status=open.

    • Ticket and remediation-plan due reminders are alerts. They are the stateful alert types Ticket due (ticket_due) and Plan due (plan_due), source compliance-engine: one alert per ticket or plan that escalates at 3 days (low), 24 hours (medium) and overdue (high), notifies once per rung, lowers when the due date moves later and resolves when the item is finished or its date moves out of the window. A restart no longer re-sends every reminder, and an overdue item notifies once instead of every day. Both can be switched off in Settings → Alert Rules. Notification rules that matched the old ticketing / remediation_plans sources or the ticket_overdue, ticket_due_soon, plan_overdue and plan_due_soon types no longer match; route the new types instead.

    • Discovery, ticket and plan notices, and identity drift, go through the alert engine. The notices Job completed, New findings and Rate limit exceeded (source discovery), Ticket assigned, Ticket status changed and Ticket comment added (source ticketing) and Plan created, Plan status changed and Plan completed (source remediation_plans) are now alert types you can switch off in Settings → Alert Rules; they keep their sources and names, so existing routing rules still match. Asset identity drift (asset_identity_drift) is now an alert on the asset that resolves on its next sighting without drift. A failed discovery job is reported once, by Discovery job failed; the separate job_failed notification is gone, so a routing rule naming job_failed no longer matches — route discovery_job_failed instead. An identity-enrichment probe that a busy sensor refused (and that is retried) no longer raises Discovery job failed.
    • The web server and the update tooling inside the images are rebuilt on current dependencies. The user-interface images serve with Caddy 2.11.9, compiled on the release's Go toolchain with its networking and JOSE libraries raised past the advisories published against the 2.11.7 build. The maintenance image's helm is now compiled from the 3.22.1 source on that same toolchain instead of shipping the upstream binary, and its cosign is compiled the same way with its libraries raised, so the pre-release image scan reports no critical or high-severity advisory in any of the 21 images.
    • Audit and change history older than a year is now trimmed. Every install gets a seeded Default (all events) retention policy (90 days hot, 365 days in total), and the daily retention job now keeps up with it: it repeats until nothing past the window is left, drops whole months at once when S3 archival is off, and runs on one audit-service replica at a time. Before, no policy existed and nothing was ever deleted. Edit the policy under Security & Trust → Retention in the admin console before upgrading if you need more.
    • Inventory shows each asset's identity in its own column. Inventory → All assets has an Identity column, on by default and in the Columns menu, reading Verified, Confirmed, Provisional or Not evaluated; the amber "Provisional identity — unverified" line under the asset name is gone (the warning colour stays for an identity conflict). A provisional asset whose sensor sighting carried a randomised (locally administered) MAC reads Private address instead of Provisional, in the list and on the asset page: such phones, tablets and laptops cannot be verified automatically, by design. Its identity status is unchanged, and the Identity filter still lists it under Provisional. The asset page no longer says a device a sensor met was "created from an advertisement"; it shows the address seen and what the last check did. See Identity evidence.

    Agents¶

    Sensors and device agents are not built or shipped by the platform. Each 6.0.0 install offers the agents release named by its signed compatibility record, shown in Discovery → Sensors & Agents → Register sensor or agent as Qualified by record …; the files are at https://github.com/VistaSecurity/VistaPlatform-Agents/releases. Upgrade the sensors and device agents you have installed to that release: open each in Discovery → Sensors & Agents and use Show upgrade steps in its detail drawer.

    What changed for installs:

    • The printed steps stop on a failed check. They stop before the install step if a download, a SHA-256 check or a signature verification fails, or if cosign is missing. cosign v3 is required on the host you install on (cosign.exe on Windows). The dialog says so, and says that Windows binaries have no Authenticode signature and macOS binaries are not notarized.
    • Upgrade steps. An agent or sensor that is behind shows Update available in its detail drawer, with Show upgrade steps: per-system commands that carry no registration code. Run with no key on an enrolled host, the installer upgrades in place and keeps the agent's identity, on Linux, macOS and Windows.
    • A new key enrolls a second agent. Registration keys are single-use, and a different key on an enrolled host enrolls another agent (which counts against a Core plan's one sensor and one device agent).
    • The platform URL is required. The installers take --url (-Url on Windows) and have no default.
    • Uninstall. sudo bash install-sensor.sh --uninstall and sudo bash install-device-agent.sh --uninstall (the macOS installers take the same option), and .\install-sensor.ps1 -Uninstall and .\install-device-agent.ps1 -Uninstall from an elevated PowerShell.
    • Old sensors get no scans. A sensor too old to take scan plans is labelled as needing an upgrade and receives no scans until it is upgraded.
    • Compose installs accept agents on the same host only. For an agent on another machine, install the platform with the Helm chart.

    Removed¶

    • Plans & Pricing → Add-ons is gone, and a lever has no add-on price. The placeholder page and its nav row are removed, and the Entitlements catalogue no longer has an Add-on column or an "add-on eligible" price on a lever. An exception or add-on is a vc_limits / vc_capabilities claim on the licence token (decision O9).
    • The storage_gb and pcap_gb_per_month levers are gone. Nothing measured either, and 6.0 has no metered billing (O8). Their cells are removed from every plan, including any override a tenant held.
    • A tier no longer carries max_sensors, max_assets, max_users, retention_days, features, limits or addon_pricing. A plan's caps and capabilities are its entitlement composition, which the resolver reads; the mirror copies could disagree with it (#812). GET /admin/tiers and GET /my-billing/subscription no longer return them, GET /tiers lists no caps, and GET /tenant/billing drops the tier's features and limits.
    • The sample tiers community, free, starter, pro and enterprise are no longer seeded. An upgrade removes each one no tenant points at and keeps any that a tenant still uses. A new tenant is placed on no tier unless the operator sets DEFAULT_SIGNUP_TIER; on a single-organisation install its caps come from the edition plan, as they already did.
    • tenant_usage and GET /billing/usage/history are gone. Usage is counted live and reported through the usage report; nothing wrote the persisted copy except a trigger that counted members without their reserved seats. The platform-admin tenant list reads API calls from tenant_resource_usage and reports storage as 0, as the unauthenticated-cache twin already did.
    • One image line: the separate Core release line is retired. Every edition now installs the same signed images and chart, docker.io/vistasecurity/<image> and oci://docker.io/vistasecurity/vistaplatform, released from one vX.Y.Z tag: without a licence an install runs as Core, and a licence selects its edition. No release is tagged core-vX.Y.Z any more, and ghcr.io/vistasecurity now carries the mirror of the one line (above), not a Core build of its own; Core releases 5.3.0 to 5.4.x stay there under their own tags and verify with their own identity (Distribution VERIFY.md). Verify a release with the release-customer.yml@refs/tags/vX.Y.Z identity. Every build now reads and verifies a licence.
    • Discovery alert settings are removed. GET and PUT /api/v1/discovery/config/alerts and the discovery_alert_configs table are gone. They were stored but never read and nothing in the product called them; the alert catalogue toggle in Settings → Alert Rules is what controls the discovery notices.
    • tenant-health-service's own alerts are removed. GET /api/v1/tenant-health-service/tenants/{tenantId}/alerts, the active_alerts and critical_alerts fields of the tenant-health board, the health_alerts table and the unused tenant_health_summary_view are gone; read the tenant's tenant_health_degraded alert from the platform alerts API instead.
    • Platform Sensor bootstrap registration is removed. cluster-sensor-service no longer registers itself per tenant or rotates a certificate, and sensor-manager no longer serves POST /api/v1/sensor-manager/sensors/auto-register. The Platform Sensor rows come from the database as before. Compose installs: drop the BOOTSTRAP_* settings and the ./bootstrap-certs volume (they are ignored).
    • The platform-log subsystem is removed. Nothing ever wrote to it, so GET /api/v1/monitoring-service/logs, /logs/{id} and /logs/siem/export (all returned empty), the platform.logs.read permission, the S3_KMS_KEY_ID, S3_REGION, S3_LOG_BUCKET, LOG_RETENTION_INTERVAL_HOURS and ENABLE_INCIDENT_HOOKS settings of monitoring-service and the four empty platform_log_* tables are gone. Audit-service's S3 archival is unchanged.
    • settings.manage is retired. The permission was in the catalogue but no route checked it; granting or revoking it changed nothing. It is removed from the permission catalogue and from every role's grant, and what a role may change in Settings is decided by the specific permission each page already names.
    • GET /api/v1/auth-service/features/availability is gone. Nothing in either UI called it and it was never in the API contract; GET /api/v1/auth-service/tenant/features answers from the same gates and is unchanged.
    • Four tables that nothing wrote are dropped, and the MSP dashboard no longer invents regions. health_benchmarks, ui_themes, tenant_geographic_data and billing_invoice_line_items are removed with their routes (/ui/themes and the MSP geographic-distribution and summary endpoints). The MSP dashboard's geographic distribution used to show fixed regions and counts when the table was empty; it now shows an empty list. A set of never-populated crypto and discovery columns (such as execution_environment and implementation_platform) is dropped from the schema as well.
    • The incident-webhook subsystem is removed. The security_incidents table and the admin-service incident hooks were never fed by anything.

    Fixed¶

    • Dialogs no longer drop keystrokes. The shared dialog re-ran its focus setup on every render, so a field inside it could lose focus to the button that opened it between two keystrokes and keep only the first character typed (seen first in New dashboard's Name field). It now sets focus only when it opens.
    • A dashboard can't be given an address the app routes elsewhere. A board named "Overview next" used to get the slug overview-next, which the retired preview's redirect catches before the board is looked up, so it could never be opened; the server now skips that slug (overview-next-2) the way it skips a name you already use.
    • One certificate-expiry alert, on your ladder. Three places used to raise certificate expiring: the 12-hourly expiry scan, every ingest of a certificate under 30 days, and the ladder you configure. The first two could escalate above your own ladder and reopen an alert the ladder had resolved for a retired certificate. Only the ladder raises it now; the scan still marks a certificate expired, once, even when two replicas scan at the same moment (a rolling update used to record the change twice).
    • Compliance follows the asset lifecycle. Denying, archiving or deleting an asset retires its findings and takes it out of framework scores at once, and approving one evaluates it without waiting for its next ingest. Retiring a removed asset's findings no longer raises a no longer detected alert.
    • Framework scores refresh when you act on a finding. Suppressing or resolving a finding, deleting an asset, and creating or deleting a threshold override re-fold the stored scores, so the framework cards and the score-drop alerts agree with the framework page. An empty override no longer replaces the platform value.
    • Findings raised outside the discovery pass announce themselves. Declared-drift, cable-drift and host-key findings, and the compliance engine's resolved control findings, now produce the finding-changed event, so their resolution raises the no longer detected alert.
    • Editing a device's name or address on the Devices form is recorded. It goes through the identity engine like every other declaration, so the asset's history shows the change and the same refusals apply (a measured value is never overwritten).
    • Expired sign-in records are deleted. Expired refresh tokens and OAuth authorization codes, which were never removed, are deleted daily once they are a day past expiry (AUTH_TOKEN_CLEANUP_INTERVAL and ADMIN_TOKEN_CLEANUP_INTERVAL change the interval).
    • The platform update dialog explains its confirm button. In the admin console, the confirm button stays disabled until you type the version, and the dialog says so.
    • A device interrogation run by the platform reports a complete result as complete. An interrogation the platform ran itself (rather than a device agent) and that found something always reported its results as not fully materialized, however completely they landed. The job now counts the findings and inventory rows the run wrote against the number of assets the device returned: all of them reads complete, any fewer still does not.
    • A brief server outage no longer signs you out. Reloading the page while the sign-in service could not be reached (a restart, a tripped gateway circuit breaker, a dropped connection) used to discard a valid session and show the sign-in page. Both consoles now keep the session, say they cannot reach the server, and retry until it answers; only a server answer that refuses the session ends it.
    • One failing request no longer takes a whole service offline at the gateway. The per-service circuit breakers counted a service's own HTTP 500 responses, so on a quiet install a single failed request (a logo upload that could not be saved, for example) made the gateway answer 503 for that service for 30 seconds. The breakers now count only network errors and the gateway codes 502 to 504.
    • Logo, favicon, profile-photo and platform-branding uploads work on a Helm install. They were written to the service's own disk, which the chart mounts read-only, so every upload failed with "Upload failed". The images are now kept in the database (new table stored_images), so they survive restarts and upgrades, are the same on every replica and are in every pg_dump; object storage is still used when an administrator configured it. A tenant logo or favicon upload also records itself in the organization's branding, and the upload controls show the server's reason when an upload is refused. Limits: a logo, login logo or photo up to 1 MB, a favicon up to 256 KB; PNG or JPEG (ICO for favicons, GIF or WebP for photos), never SVG.
