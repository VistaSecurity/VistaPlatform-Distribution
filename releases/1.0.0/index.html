    Vista Platform Core 1.0.0 — full list of changes¶

    Released 2026-09-21. The release summary — highlights, what breaks, what each edition includes, and how to verify the signatures — is in the CHANGELOG published with that release. This page is the complete, per-change record behind it.

    1.0.0 replaced the asset model, so its entry is far longer than a release entry normally is; keeping it here rather than in the changelog is what lets the changelog stay readable.

    Trustworthy discovery RC rollout¶

    The staged RC enhancements distinguish established, operator-confirmed and legacy identity from monitoring approval, type and assessment coverage. Weak observations are retained outside Inventory, with source evidence, explicit confirmation/link/ dismiss decisions and separate counts. Reviewed merges select a survivor and sources, check a current server preview and preserve associations and audit history. There is no merge undo or split workflow.

    The coupled enrichment release queries configured sources before bounded DNS and TLS/SSH checks through a suitable observing collector. Existing credentials, network exclusions, protocol policy and sensitive-device restrictions still apply. The tenant's Trustworthy discovery settings control prospective activation and pause; existing records remain visible and keep their identities and associations. Once activated, pause retains incoming evidence instead of restoring permissive asset creation. See the operator guide.

    Admission-enabled acceptance passed all 310 required checks across the three estates, every reference stage, restart/resume and two distinct certificates on one asset. Canary baseline reconciliation, the required 24-hour/two-cycle canary and live Windows deployment acceptance remain separate operational gates. Historical failed acceptance runs remain preserved.

    Added¶

    • Inventory shows a device heard advertised on another, configured tenant network as a provisional item — visible, unverified, excluded from the asset allowance until a collector on the device's own network corroborates it in place (same asset id, same history). (#1898, #1900, #1901)

    • Tickets can be raised directly from Remediation → Queue, for any subject, without starting from a finding or an alert. Filing a ticket no longer requires the permission to resolve one — a viewer who spots a problem can report it; editing, commenting and deleting stay privileged. (#1911)

    • Ticket categories now follow the finding producer one for one — compliance, cryptography, post-quantum, certificate, vulnerability, lifecycle, inventory, configuration and drift — so the work queue's category filter separates them. Every new ticket also carries a default due date derived from its priority, which is what the overdue and due-soon views and notifications act on. (#1911)
    • Remediation → Progress: opened against resolved over time, average resolution time, per-category backlog and post-quantum readiness. (#1911)
    • Tickets can be edited in place — assignee, category, priority, severity, due date, tags, resolution notes and an external ticket link — and deleted, with the deletion and the ticket's content recorded in the audit trail. (#1911)

    • Three further dashboards under one Dashboard section — Assets, Compliance and post-quantum readiness — alongside the existing Overview, which is unchanged. The post-quantum page surfaces the per-algorithm-family migration worklist and the catalogue's recommended replacement. (#1907)

    • Device agents can report bounded outbound connections on segments without a sensor. Deploy the updated device-agent binary first, then opt in locally with HOST_INVENTORY_CONNECTIONS_ENABLED=true, or set collect_connections: true on a remote host-inventory job. Existing agents and default settings do not begin collecting peers after a platform upgrade. Each snapshot is coalesced and capped at 256 peers; local ephemeral ports do not create new identities, and accepted TCP connections are excluded. Public destinations become external connections attributed to the reporting host. Private destinations follow existing network ownership and approval rules; registering an auto-approving network promotes the existing pending asset on a subsequent collection. Windows peer collection is TCP-only; Linux and macOS also report connected UDP peers when the OS exposes them. Peerless UDP bindings remain unknown-role facts, rather than claimed listening services. The support command --host-inventory-once excludes outbound peers. See Host inventory. (#1876)

    • An endpoint that has gone quiet is now marked stale. asset_endpoints.status has allowed active / stale / closed since the table was written and nothing ever wrote stale, so a filter on it returned nothing. The hygiene pass now moves an endpoint to stale once nothing has observed it for 30 days — the same boundary as the Stale finding — and back to active when something sees it again. closed is untouched: that is an authoritative "the host says this socket is gone", and only a host inventory writes it. The exposure rules stop judging an endpoint once it goes stale — an unobserved socket is not a measured exposure — but they no longer resolve its findings either, and port-profile drift still counts the port as present: "nothing has looked" must not reach a user as "the port closed" or as "the exposure is fixed".

    • Port-profile drift findings name the endpoints that changed. A port_profile_changed finding listed the ports that opened and closed but not which face they appeared on; it now carries each endpoint's address and id, so a host with several addresses says which one moved.

    • Vulnerable to quantum attack findings now name the KEY, not only the service and the certificate. The finding registry has always declared pqc_vulnerable as being about a crypto configuration, a certificate or a key, and nothing produced the third. The key is usually the subject a migration is planned against: a public key is recorded once in the key inventory and shared by every certificate and service presenting it, so one RSA key across forty hosts is one migration rather than forty. The crypto producer now classifies each key in use against the same NIST IR 8547 denylist of Shor-breakable primitives it applies everywhere else — symmetric keys raise nothing, post-quantum keys raise nothing, and a key whose algorithm resolves to no catalogue row is unclassified rather than assumed either way. Only keys actually linked to an asset are judged. Key findings are reachable from every asset using the key — finding:(…), the has_findings facet, the asset page's Findings tab and the risk roll-up all resolve through the one subject walk, which learned the key path in the same change.

    • A sortable "Last checked" column on Inventory → Software, and a "least recently checked" sort. When the lifecycle catalogue last had an answer for a product was already recorded but reached the UI only as a tooltip, so "which of my products has nobody looked at lately?" could not be answered without hovering every row. Products no completed pass has ever recorded an answer for sort FIRST, ahead of long-ago-checked ones: that is the weaker state, not a missing value. GET /software/products gains sort=eol_checked.

    • The command palette's ask mode now renders asset-class and relationship rows too, like its search mode — it rendered asset rows alone, so the same question offered different answers depending on whether it was typed as a search or asked in words.

    • A Class history panel on every asset, recording every class it has held. Core. An asset's class is an input to most of the platform — which findings a producer writes, which approval rules match, which compliance measurements apply — and it lived in a single mutable column. Change it and the previous answer was gone: nothing anywhere could say a printer had ever been a printer, so a finding written before the change was indistinguishable from one written after it, and "was this thing reclassified?" had no answer. A new asset_class_history table records one row per transition, with both ends named, the mechanism that moved it (set at discovery, accepted in Approvals, edited by a person, stated by an import), the person when there was one, and the rule ids or model id behind it. Written at all three places a class can move, inside the same transaction as the change. Read it on Inventory → an asset → History, above the general change log. An empty panel says "no recorded class change", not "never changed" — an asset created before this record exists has no entry, which is a different claim.

    • An interrogated neighbour's class is now argued from what it advertised, not from its MAC prefix alone. Core. A device reported over LLDP or CDP — by a Cisco switch, a Palo Alto firewall or a UniFi controller — reached the classifier as a MAC address and nothing else. An OUI names a manufacturer, and every manufacturer that matters makes switches, access points and desk phones alike, so almost every neighbour came back "Unknown host" while the interrogators were parsing, and then discarding, the device's own statement of what it is. The advertised product, software version and 802.1AB/CDP capability bits now travel with the peer and reach the classification rules. Each is a strict projection, never a copy: the product is the segment before the first comma of a system description and the version is the version token, because a system description is free text an operator can put a secret into. And a segment that names a credential at all — "snmp community …", a password, a key — is dropped whole rather than kept, so the defence does not rest on the operator having typed the product first.

    • A "Changed since baseline" alert. Core. The drift producer has been writing findings — a device class never seen on a segment before, a protocol an asset has not spoken, a changed set of listening ports, a certificate from a new issuer — with nothing on the Alerts page ever mentioning them. There is now a drift_detected alert type, on by default and switchable under Settings → Notifications & Alerts → Alert Rules, raising one alert per subject and grading it by the worst open drift finding. Its severity is the finding's own: drift has no second scale (no CVSS, no deadline) to grade on, so inventing one would be a second opinion about a judgement already made. It auto-resolves when the findings stop being detected — which includes somebody resolving one because the change was planned.

    • The subject of an alert is a link. Core. Remediation → Alerts rendered the Subject column as plain text, so the page that exists to be triaged told you which asset and then left you to go and find it. Asset, software install, crypto configuration, control and certificate subjects now drill straight through. Subject types with no id-addressable destination yet (sensor, agent, discovery job, framework, and the platform-track subjects) stay plain text deliberately: a link that lands on a page which cannot resolve the subject reads as "nothing wrong here". The install and configuration links name the findings lens explicitly, because the Findings page's crypto-risk lenses cannot honour a subject filter — landing on one would have shown an unfiltered list under a banner claiming it was filtered.

    • The End of life column on the Software tab and the Software lens now gives a supported package its credit. Core. It used to read "Not assessed" for every install without an end-of-life finding, because nothing on the install said whether the lifecycle catalogue had resolved it to a supported cycle, had it with no published date, or had never heard of it — so a supported package and an unknown one looked identical. The eol producer now records, per install and in the same transaction as its findings, what the catalogue resolved, and the column reads that record: Supported until 2028-04-01, No date published, Not in catalogue, or Not assessed — the last now meaning only that no completed check has recorded an answer (the check has not run since the install was seen, the install is no longer present, or its finding was closed). Hover a cell for the date the catalogue was last checked. Nothing re-runs the resolution in a list query; a closed finding does not turn into "Supported". GET …/software and GET /software/products carry the widened eol_state and a new eol_assessed_at.

    • The auto-accept threshold now covers every way a sighting reaches us (asset-inventory workstream 4.6a, ADR-0002 D3). Core.

    Setting a matcher score at or above which the platform may merge two of your assets without asking used to govern inventory intakes only. Device interrogation, the cloud collectors, and the neighbours an interrogated device reports went through a different identification engine that did not read the setting — so those sightings were never auto-accepted, whatever you had set. That failed safe, and it was disclosed rather than hidden, but the same host reaches the platform both ways: which collector happened to see it decided whether your threshold applied.

    It applies to all of them now. The threshold is read per sighting, on the transaction that resolves it, so turning it off takes effect on the very next observation. Nothing else about it changed: the same four conditions still have to hold — you set a threshold above zero, the score is at or above it, no serial / cloud id / agent id / CMDB sys_id disagrees, and every asset involved is already in service, not still waiting in Approvals — and every auto-accepted merge still writes an audit event and appears on Discovery → Approvals under "Auto-merged by the matcher (last 30 days)", whichever collector's sighting caused it.

    The scope sentence on Settings → Policies → Identification rules and in the Asset approval guide has been corrected to match.

    • Interrogated neighbours can now be classified through Approvals (asset-inventory workstreams 4.6a, closing a 2.10b/4.2 limit). Core.

    When a switch or firewall reports its neighbours, the platform runs your classification rules over what it learned about each one. Where a neighbour was a host the inventory already held, the answer was computed and then thrown away: a device your rules clearly identify stayed Unknown host for ever, and nothing said an answer had been discarded.

    Those answers now appear as class proposals on Discovery → Approvals, exactly as they do for a host a sensor discovers — with the rule they came from cited, and the class the asset holds today shown beside the proposed one. A class is still never overwritten, and a class the learned classifier proposed is still marked as inferred rather than as a rule, so what argued for a class stays auditable.

    • A model provider can now be configured through the chart (ADR-0008, gate 4). A new ai: block in values.yaml — provider, baseUrl, model, allowPrivateEndpoints, maxTokens, timeout, and an apiKey block naming the environment variable and an operator-supplied Secret — renders the AI_* settings into the shared app ConfigMap and injects the credential on every backend. Before this there was no AI_* value anywhere in the chart, so on the shipped Helm path no generative capability could ever answer, whatever edition was installed.

    It is off by default and the product is complete with it off: every AI capability has a rule-based behaviour behind it, and Settings → AI assistant states what that behaviour is per capability. When ai.provider is empty the block renders nothing at all, so an existing release's ConfigMap is byte-identical across the upgrade and the checksum/config annotation does not roll every backend.

    The credential reaches every backend rather than only the four that own a seam, deliberately: GET /tenant/ai is the single availability answer both UIs read before rendering any AI control, auth-service serves it and owns no seam, and the Anthropic client refuses to construct without a key — so a narrower injection would hide every AI control in the product while the capability underneath it worked. A misspelled provider is refused at install time by values.schema.json rather than degrading to "no provider" with a warning in a pod log. New operator guide: docsv4/core/operate/configuration/ai-provider.md.

    • The drift finding producer (asset-inventory workstream 4.7, ADR-0005 D3). Four kinds, judged against the tenant's own recent history rather than against any catalogue: new_class_in_segment, unexpected_protocol, port_profile_changed and new_issuer. All four write through the shared shared/findings/producer writer and run in the nightly finding-producer job beside eol and vulnerability.

    The baseline is a window, and the window is the tenant's. tenant_admin_settings.config.drift.baseline_days (default 30, bounds 7–365) is read on every pass and never cached, and is edited under Settings → Asset Lifecycle → Drift baseline. Everything first observed inside the window is a candidate; everything older is the baseline. No new table: every baseline is derived from timestamps the inventory already carries (assets.first_discovered_at, asset_endpoints.first_seen_at/last_seen_at, crypto_implementations.first_discovered_at).

    Nothing is drift without something to compare against. A tenant observed for less than one full window raises nothing and sweeps nothing — "we have not been watching long enough to tell" is not "the condition went away", and a new organization is not told that every asset it owns is new. The same rule applies per subject: an asset with no protocol, port or certificate history older than the window, and a network segment newer than the window, are reported as un-evaluable rather than as changed.

    A drift finding closes when the change ages INTO the baseline, as well as when the condition disappears. And an observation_key on every finding means a person's decision survives: resolving "started speaking SSH" is not undone by the next pass, while a genuinely different observation on the same host re-opens the finding rather than being swallowed by the earlier resolve. Suppression, being a standing decision about the condition, is never re-opened.

    Coverage is what the pass could compare. Every completed pass records its coverage through Writer.MarkAssessed, in the same transaction as its findings and its sweep (workstream 3.2), so drift joins an asset's risk_assessed_by — but only where that asset had a history of its own to be compared against, plus any asset a finding was raised on. An asset first seen inside the window, and every asset of an organization still warming up, are deliberately NOT claimed: "we could not compare yet" must not read as "we compared and it was fine".

    Evidence carries the baseline, the observation, the window bounds and the timestamps — and for new_issuer, the issuer DN and the certificate fingerprint, never the certificate body. Loopback-bound sockets (bound_local = true) are excluded from the port profile; sockets whose binding is unknown are kept, because that is every endpoint a network scan found. The Findings inspector renders the two sides of the comparison side by side.

    • The configuration and hygiene finding producers (asset-inventory workstream 3.5, ADR-0005 D3), on the shared writer the eol and vulnerability producers landed with.

    Configuration judges how a device is managed and what it exposes. Two sources, both already collected: the mgmt.plaintext / mgmt.protocol facts device interrogation writes — the SNMP v2c seed is the first plaintext_management finding — and a reviewed Go rule table over asset_endpoints covering Telnet, FTP and SNMP v1/v2c management, plus unauthenticated datastores (Redis, memcached, MongoDB, Elasticsearch, etcd, CouchDB), the plaintext Docker API and kubelet read-only port, rsh/rlogin, and NFS/rpcbind/TFTP. Three restraints are the substance: a port rule is suppressed the moment something MEASURED the service and it was not that one (the host naming HAProxy on 6379 beats the port); no rule fires on an endpoint measured behind TLS or SSH; and a loopback-bound socket is not an exposure, with bound_local kept three-valued so "nobody established it" never renders as "reachable". Every finding records which signal fired and cites the rule id.

    Inventory hygiene judges the record rather than the thing: no_owner, no_class, no_location, duplicate_suspected (raised on BOTH halves of a pending merge proposal, and resolved when Approvals decides it), stale on a 30/90/180-day ladder across assets, endpoints and software installs, and orphan_relationship on edges whose other end was archived or deleted. Every kind is feeds_risk: false and scores 0 — data quality is reported beside risk, never inside it.

    Both producers record what they examined in the coverage record, which is what turns the controls that COUNT their findings — Inventory Hygiene IH-005 and IH-006, and the new mgmt_plaintext — from "not assessed" into a real number, including a real zero. Configuration claims only assets it had something to look at: a host with no management fact and no active endpoint is read and deliberately NOT claimed, so "nothing was collected here" cannot read as "we looked and it is fine". Hygiene never reaches the risk-assessed array — it feeds no score, and an asset whose only evaluation was a missing owner has not had its risk assessed.

    default_credentials_exposed stays registered and unproduced, deliberately: nothing in the product records that a vendor default was ACCEPTED, and raising the kind from anything weaker would report an inference as a measurement.

    New measurement type mgmt_plaintext over the finding shape, with a new via: asset_or_endpoint so a control counts a Telnet listener found on an endpoint as well as one recorded on the asset.

    • Ask about your inventory in words, and get back a query you can edit (asset-inventory workstream 4.4b, ADR-0006 D2/D9, ADR-0008 D1). Enterprise.

    The Query seam had a constructor and no caller. It has three now: a POST /api/v{1,2}/inventory-service/ask endpoint, the vistaplatform_ask MCP tool, and an Ask mode in the ⌘K command palette.

    What comes back is a query, not a chat reply. A question becomes ONE line of the query language, validated against the production catalogue before anything runs; the response is the canonical predicate that ran — the platform's own default scope AND-ed in — then the assets it selected, then a summary in which every sentence cites one of those assets. "Open in Inventory" takes the predicate into the query editor, where it can be changed, re-run and saved as a view. A client rendering only the query and the rows has the whole answer.

    A refusal is an answer. When the model cannot write a query that validates, the endpoint returns 422 carrying the validator's own {code, message, span, suggestion} diagnostics, in the same wire shape a hand-typed query's 400 uses, and the palette renders them through the query editor's own renderer with a button to open the attempt for editing. "No field hostnaem on assets — did you mean hostname?" is a better answer to a mistyped question than a confidently wrong list of servers.

    Nothing matched is a fact about the query. Zero rows gets a fixed sentence the platform writes itself and no narration turn at all: an asset nobody has recorded and an asset that does not exist look identical from here.

    The route is mounted in every edition and a Core build answers 402 — the availability question already has one deployment-wide answer at GET /tenant/ai, and a 404 would be indistinguishable from a broken route. 403 for the tenant kill switch, 503 for no provider. Gated on assets.read, the permission the MCP asset tools already declare for the same rows, pinned both in the middleware and in the routing table.

    The MCP tool refuses honestly. On a deployment that cannot answer it returns {"available": false, "reason": …} as a result, naming which of edition / provider / a tenant switch is in the way and what to use instead — never a fabricated answer, and never a tool error for something a retry cannot fix. A permission failure stays a real error: the kill-switch 403 identifies itself with reason: assistant_disabled, and every other 403 — a role without assets.read, a scope-narrowed API token, a missing CSRF token — falls through to a real error carrying the platform's own sentence, rather than being told the organization switched something off.

    Its bounds are the endpoint's own. A question past the published 4096-byte cap is a 400 naming the cap, not a 500, and one question is bounded end to end by a budget that fits inside the connection's write timeout — so a slow answer arrives as an error somebody can read instead of as a dropped connection.

    The question is never written to the MCP audit rail. It is the one argument on that surface that is a prompt, and ADR-0008 D4.7's opt-in is enforced at the provider boundary; a copy elsewhere would be an opt-in honoured in one place and bypassed in another. The canonical query is recorded either way — it is the platform's own output, and it is what answers "which assets did that call select".

    The palette also gains ADR-0006 D9's two missing result kinds in ordinary search: asset classes (from the generated taxonomy, no request, opening the whole subtree) and relationships of the best asset match, which is the shortest route to "this switch is being replaced on Friday — what is behind it?". Both modes now share one result model, so an asset row cannot look different depending on how it was found.

    • Per-asset risk is recomputed across every producer, and says who has looked (asset-inventory workstream 3.2, ADR-0005 D4).

    The crypto producer. The cryptographic judgements the product has always made are now findings like everyone else's: crypto/weak_configuration on a configuration whose components the algorithm catalogue rates weak (worst component wins, with every component and its rating carried as evidence), crypto/weak_certificate on a certificate whose key algorithm, key size or signature is weak — the SP 800-131A floor applied per algorithm FAMILY, so a healthy 256-bit elliptic-curve key is not measured against the RSA floor — and crypto/pqc_vulnerable on either, from the same NIST IR 8547 denylist /pqc/progress counts with. Nothing here holds a second opinion: the catalogue roles, the PQC classification and the key-size and broken-hash rules all moved to one place each (internal/cryptoassess, shared/cryptoparse) and both callers read them.

    One rollup, over findings. assets.risk_score is now MAX over the asset's OPEN risk-feeding findings — the asset itself plus its endpoints, configurations, certificates and software installs — filtered by the registry's feeds_risk flags rather than a list in code, so a hygiene finding can never inflate a security score. It replaces a statement that could only see crypto configurations, which meant an end-of-life OS or a critical CVE moved no asset's number. Parity with the old statement is PROVEN rather than asserted: both are computed over the same rows in one test before the old one was deleted.

    Coverage is recorded, not inferred. A new producer_assessments table records which producer has completed a pass over which asset, written inside the pass's own write transaction — so a failed pass claims nothing. assets.risk_assessed_by is derived from it as its RISK-feeding subset: the record covers every producer, the array carries only the ones whose findings can move the score, so an asset only inventory hygiene has visited still reads NOT ASSESSED for risk. Score 0 with producers named is "assessed, nothing found"; score 0 with an empty array is NOT ASSESSED, and the asset page says which in those words. The asset's Overview tab also names the single finding its score came from, and clicking it opens the Findings tab with that finding highlighted. Compliance's finding measurement shape now gates on the full coverage record rather than the array, which is what makes an assessed_by: hygiene control answerable. A subject reachable from several assets covers all of them — a wildcard certificate served by four hosts raises four assets' risk, so it marks four.

    Every producer pass now ends with one generic set-based recompute, so the configuration, hygiene and drift producers get it without knowing it exists. Discovery that writes a crypto configuration triggers a pass for that tenant rather than computing risk in the ingest path.

    • Three new alert types: vulnerable software, end of life, and an inventory hygiene score drop (asset-inventory workstream 3.9, ADR-0005 D7).

    Vulnerable software. An installed package matching a published advisory now opens ONE alert for that installation — not one per CVE, because the fix is the same either way — graded on the CVSS qualitative severity bands (Medium from 4.0, High from 7.0, Critical from 9.0) by the worst advisory that matched, escalating in place when a worse one turns up. Advisories below CVSS 4.0 and advisories the feed has not scored stay visible as findings on the asset and open no alert: a notification threshold, never a claim of cleanliness.

    End of life. An operating system, a package or a piece of hardware approaching or past the date its vendor stops shipping fixes opens ONE alert for the SUBJECT — an asset whose OS and whose hardware are both affected is one piece of work, graded by whichever is worse and naming both — on a ladder in days: 180 low, 90 medium, past high, past by more than a year critical. The alert grades the deadline; the finding behind it still grades the blast radius, and it is the finding that moves the asset's risk score.

    Both are driven by the eol and vulnerability producers' OPEN findings, read through the ONE generated open-finding predicate (shared/findings.OpenSQL), and both auto-resolve when nothing on the subject crosses a rung any more. A pass raises only when the alert is new or the rung has risen.

    Inventory hygiene score drop. The Inventory Hygiene framework's score falling more than 10 points in 24 hours is now its own alert type rather than a compliance_score_drop, so it can be routed — or silenced — separately from security posture. It is the SAME detector, routed by framework code; the two types gate independently.

    The alert registry gained a second ladder shape to carry these: a fixed ladder, declared whole in standards/alert-registry.yaml as rungs: [{threshold, severity}], for types whose boundaries come from a published standard or from the finding ladder the alert is driven by. Nothing in a fixed ladder is tenant-tunable, so Settings → Notifications & Alerts → Alert Rules shows its rungs with no editor beside them.

    • A learned classifier, underneath the rules and never in front of them (asset-inventory workstream 4.2, ADR-0008 D1/D2/D3/D4.3).

    Most OUI rows in the classification catalogue are vendor-only, because most manufacturers sell across several classes under one assignment. So an HP MAC on a box with 9100 open and an embedded web server is obviously a printer to a person and unknown_host to the catalogue. That population — the rules were silent, or the rules contradicted each other — is what this is for, and it is all it is for.

    The Classifier seam is now a chain. The curated rules run first and are unchanged: a rule that decides gets the answer, with rule provenance, and the model is not consulted, cannot outrank it and cannot soften its confidence. The model speaks only where they could not, and even then it must clear four further refusals — a 0.80 probability floor, a class the LIVE rule vocabulary contains, and, on a rules conflict, one of the classes the rules themselves named. Each refusal was mutation-checked by deleting it and watching a named test fail.

    It proposes; it never sets a class. Not on an existing asset, and — the half that is easy to get wrong — not on a new one either. A rule-derived class IS written at creation, because the asset waits in Approvals and approving it approves the class; a model's answer always becomes an Approvals row instead, stamped class_source_kind: inferred with class_source_ref: model:<id> rather than rule. Both spellings satisfy every database constraint, so nothing but that distinction stands on the one column a reviewer uses to audit a class.

    The row says "proposed by model (P=0.87)" and lists the three feature contributions the score is literally made of — "port 9100 is open", "the MAC prefix is registered to Hewlett Packard". A model cannot link to a source the way a rule can, so those reasons are the whole of its argument; and they name features and evidence, never a hostname or an address, because the classifier's entire input carries neither.

    shared/classify/model: a multinomial logistic regression over hashed categorical features — OUI vendor, SNMP enterprise arc, product-id family, Server: banner tokens, 64 well-known ports chosen for what they separate, mDNS service types, LLDP/CDP capability bits, tokenised cloud resource type, and the rule engine's own output — a ~1,000-name space of which 260 carry a trained weight. Weights embedded in the binary, evaluated in pure Go. No ONNX runtime, no CGO, no new dependency — which closes the "in-process inference runtime" question the build plan had left open. Trainer at cmd/train-classifier over 184 committed fixtures, 131 of which the shipped rules are silent on, including the traps: a VM with a Cisco product id, a printer serving Apache, one Ubiquiti prefix that is both an access point and a switch, and ten class_rejected rejections trained as constraints rather than invented labels. Weights are reproducible from the fixtures by test, and the temperature is calibrated on held-out logits — fitted in-sample it is a sharpener, not a calibration, and would have made every probability read 0.999 and the floor meaningless. 1.0000 in-sample, 0.9310 five-fold held out, and — the number a reviewer actually experiences — 0.9640 precision above the 0.80 floor on the inputs the chain would raise a proposal for. The floor bounds the wrong proposals rather than eliminating them, which is what a calibrated threshold can do; a person accepting the row is what stops one reaching an asset. Both the per-class calibration table and the held-out log-loss are measured at the temperature that ships.

    • Four kinds of bill of materials on one artifact pipeline, and an OCSF export (asset-inventory workstream 3.7, ADR-0005 D6).

    The CBOM was never a format — it was a subset. POST /cbom/generate gains kind: cbom (unchanged, and the default), sbom, hbom or inventory. CycloneDX 1.7 already models the union — device, operating-system, platform, application, library and data components, services for network faces, dependencies for edges, vulnerabilities for CVEs — so all four share one format, one content hash, one signature and one comparison rather than each inventing a serialisation. A request that omits kind is unchanged in meaning as well as in shape, and a CBOM's canonical bytes are byte-for-byte what they were: every new CycloneDX field is omitempty and appended, never inserted, because those bytes are what every stored artifact's hash and signature refer to.

    What each kind holds. An SBOM is one component per software product — a fleet of 500 hosts running the same OpenSSL is one thing to patch, with the hosts underneath it as evidence.occurrences — and carries no dependencies graph, because an install record says a product is present, not that anything depends on it. An HBOM is one device per hardware-class asset with its hw.* facts, membership decided by the class registry so it cannot drift from the taxonomy. An inventory is every asset typed by its class, endpoints as services, approved relationships as the dependencies graph, facts and identifiers as properties, and open vulnerabilities.

    Only the vulnerability producer's findings become CycloneDX vulnerabilities. Compliance failures, EOL, hygiene, configuration and drift are findings; none is a CVE, and every tool reading CycloneDX treats that array as CVEs. A missing asset owner listed there would be read as a remote code execution. A CVE the catalogue has not scored carries no rating at all — a 0.0 reads as "scored, and harmless".

    OCSF 1.9.0 export, Core, at ?format=ocsf on an inventory artifact: JSON Lines, one Device Inventory Info (class 5001) per asset and one Vulnerability Finding (2002) per vulnerability. It is a projection of the stored artifact, so what a SIEM ingests is exactly what the content hash covers, stamped with the artifact's own generation time rather than the download's. Where OCSF defines a field nothing measured, the field is absent — not "", 0 or "Unknown" — and an asset class with no OCSF counterpart is type_id: 0 (Unknown), never 99 (Other): "we do not know" is a claim about us and true, "OCSF does not model this" is a claim about OCSF we are not entitled to make. This reaches parity with runZero, the only other product in the category exporting CycloneDX CBOM or OCSF.

    Refusals rather than plausible-looking output. Comparison is same-kind only (400): two kinds identify contents in disjoint ways, so a cross-kind diff would report the entire base removed and the entire head added — precise, confident, meaningless. OCSF is defined only for inventory, and other kinds get a 400 naming the kind rather than an empty stream that reads as "no assets". SPDX and PDF stay CBOM-only, after the existing 402 edition gate so Core's answer is unchanged.

    UI: Risk & Compliance → Bills of Materials (was "CBOM" — a user wanting an SBOM would never have looked there; the route is unchanged). The Generate dialog gains a Kind picker with one line per kind saying what it contains; the list gains a Kind column and filter; the download control offers only the formats that artifact's kind can produce; Compare restricts each side to the other's kind and says why.

    Two bugs the tests caught before shipping: Contains(os_name, "ios") reported FortiOS, IOS-XE and Cisco IOS as Apple mobile devices, and a fact with two sources is stored per-source, so the OCSF lookup found nothing for exactly the assets carrying the most evidence.

    • Registry-driven compliance measurement, and two new Core frameworks — Inventory Hygiene and Lifecycle (asset-inventory workstream 3.6, ADR-0005 D5).

    What a control can measure is declared, not coded. It used to live twice: as a switch of nineteen hand-written SQL blocks in the compliance-engine, and as nineteen INSERTed rows in seed.sql, with nothing holding the two together — a control could name a measurement type the extractor did not implement (it evaluated to nothing and read as "not assessed" forever), and the extractor could implement one no seed row offered. Both halves now come from standards/measurement-types.yaml. A row declares a whitelisted shape (one of five reviewed FROM/JOIN skeletons), a value that shape offers, and a query-language predicate compiled by shared/query; one executor runs all of them. No SQL comes from the registry, and the statement each row compiles to is pinned in a golden file, so a registry change is reviewable as the query it will actually run.

    The refactor changed nothing, and that was proven rather than asserted. The old extractor was kept for exactly one commit as a test oracle, and both implementations were run over one deliberately awkward fixture — a soft-deleted asset, a soft-deleted configuration, a certificate with no algorithm at all, a CA certificate, a post-quantum key belonging to neither key-size family, an endpoint with no address, a configuration with no endpoint — and required to agree on all 74 measurements, tenant-wide and per-subject. They did. The oracle is gone; the golden it recorded stays, so every future change to a shape, a transform or a predicate is still measured against what the original extractor produced.

    Inventory Hygiene (6 controls) scores the inventory record: is every asset owned, classified, located and recently seen, and are there suspected duplicates or relationships pointing at deleted assets? Nothing here feeds an asset's risk score — a host with no owner is not less secure, it is less manageable. Lifecycle (4 controls) tracks what has outlived its vendor: operating systems past end of life and within 90 days of it, software past end of life, hardware past end of support. Both are Core, both activatable like Certificate Hygiene, and both ship in the free seed rather than the Enterprise content bundle.

    Both are three-valued, which is the point. A lifecycle control over an asset whose operating system the end-of-life catalogue never resolved a date for reads not assessed, never "supported": "we could not find out" and "it is fine" are different answers, and a report that conflates them is worse than none. The two counting hygiene controls read not assessed until the platform's hygiene checks have actually evaluated the asset, so a count of zero from a check that never ran is not shown as a clean bill of health.

    The catalogue is the registry.     The NetBox connector (Enterprise, connector_netbox) pulls sites, prefixes, VLANs, device types and devices. Prefixes become network_segments with imported provenance; devices become observations through the identification engine, so a device a sensor also found is one asset.     It never writes to NetBox. The token needs read access only, and drift is a read-only view: what NetBox lists and we do not, and what we hold and NetBox does not, each row linking into NetBox. Filling a source of truth with our own guesses would destroy the only thing that makes comparing the two worth doing.     • When two rules disagree it proposes nothing, and shows you both candidates to pick between. Two rules arguing is a problem with the rules, and that is a thing to fix rather than a coin to flip.
    • A rejection sticks. Say no once and the same class is not proposed again for that asset — otherwise a printer announcing itself every few minutes would put the same question back in your queue all day.

    The restraint is deliberate: 802.1AB bridge on its own proposes nothing, because access points and desk phones bridge too; telephone proposes nothing because the taxonomy has no phone class to map it to; and a device advertising that it BOTH routes and switches is proposed as a Network device rather than guessed at, because a layer-3 switch and a router with a switch module advertise exactly the same thing.     • The host agent's inventory of its own machine now becomes an asset. Since the last release the agent has been able to describe the host it runs on — OS and kernel, hardware identity, installed packages, listening sockets, trust stores — and the platform stored every collection and did nothing with it. It now materialises.

    After a collection you get one asset per host, waiting in Discovery → Approvals, carrying:

    • its facts — OS, kernel, hardware vendor/model/serial, interfaces, and two new ones summarising its trust stores (how many certificates, and how many things in them are not certificates at all);
    • one endpoint per listening socket, with the process holding it and an Exposure column reading "bound to localhost" or "reachable" — the half of a host's exposure a network scan structurally cannot see. That column is blank for everything a scan found, deliberately: a scan sees what answers, not what a socket is bound to, and showing those as "reachable" would be an exposure claim nobody measured. It is filterable too (endpoint.bound_local = false);
    • its installed packages, in the asset's Software tab and the Inventory Software lens, beside anything an SBOM upload put there.

    Things it deliberately does not do:

    • It does not guess what kind of machine it is. The class stays Unknown host until a classification rule decides otherwise. An OS name and a hardware model are evidence; calling that a server is a judgement, and a plausible-looking guess is the kind that gets approved without being read.
    • It does not merge two machines that share an agent id. A restored image or a cloned VM carries the agent's identity onto different hardware; the platform opens a merge proposal naming both rather than quietly giving one asset two hardware serials.
    • It does not report a failed step as an empty answer. A host whose package database could not be read records no package count and leaves its software list exactly as the last good collection left it — rather than marking everything on it as uninstalled. The same holds for its listening sockets.
    • Nothing is deleted. A package that is gone is marked removed and a socket that has stopped listening is marked closed; both keep their first-seen date, so "this was here in March" stays answerable. Endpoints that an active scan or a cloud connector found are never retired by an agent — it is only authoritative about its own host.

    What the platform will and will not say about such a device:

    • A hardware address alone is enough. An ARP frame from a camera that answers no name and holds no address still says the camera is there. It becomes an asset keyed on its MAC, and the next sighting — with a name, or a new address — updates that asset rather than adding a second one.
    • Its name is what it called itself. No reverse lookup is performed on these devices: internal host names stay internal. That is now enforced by a test that drives the real ingest with the resolver replaced and fails if anything reaches it.
    • Its type comes from the classification rules, or stays "Unknown host". A device advertising printing is a printer, and saying so is a rule's conclusion with a citation behind it — see the classification entry above. A device no rule recognises stays "Unknown host", which reads as "we have not worked this out" rather than as an answer.
    • A randomised (locally administered) MAC is not used as identity. Phones and laptops rotate those, and keying on one would add a new asset every rotation.
    • It has no ports, services or certificates, because nothing connected to it. A blank crypto section on one of these means nobody looked, not that it came back clean.

    Auto-approval rules can name these rows specifically — kind:host_observation and network.segment_id=… — so a tenant can accept the devices a sensor sees on a segment they own without also auto-approving every TLS endpoint that sensor reports. A segment is matched from the device's address, so a device seen without one (an LLDP frame carrying only a chassis ID, an ARP probe from a host that has not been given an address) still waits for a person. We would rather queue it than place it on a segment nothing measured.

    • A sensor's host-observation counters are visible. The sensor has been reporting eight of them on every heartbeat, and sensor-manager mapped a fixed set of columns onto the metrics table and dropped the rest — so they were documented, sent, and stored nowhere. Discovery → Sensors & Agents → a sensor → Health now shows how many devices the sensor has seen this way over the selected range, how many observations it had to shed, and how many subjects are accumulating right now. A non-zero shed count means the segment is busier than the sensor is sized for, and devices on it may be missing.

    • Host inventory: one collector, local and remote, held at intake. The device agent can now inventory a host as well as interrogate a network device — its OS and kernel, hardware identity, installed packages, listening sockets, and installed certificate stores (asset-inventory ADR-0004 D3, workstream 2.11a).

    One collector library, two ways in. shared/hostinventory runs the same command set through a Runner: locally via os/exec, or remotely over SSH with the device's stored credentials. The parsers take command output or file bytes and nothing else — they never touch os/exec, read a local path, or consult runtime.GOOS — so local and remote parity is a property of the shape rather than something anyone has to maintain. A test drives one fixture through both transports and requires byte-identical reports.

    • Local mode is off by default (HOST_INVENTORY_ENABLED, HOST_INVENTORY_INTERVAL, default 24h with a 1h floor). It is not a job: the agent describes its own host on its own schedule, with no credentials, and posts to a new agent-authenticated intake route. An agent installed to interrogate firewalls does not start enumerating its own host because it was upgraded.
    • Remote mode is a host_inventory job queued against a device that already has SSH credentials, and requires mode: "remote" plus an agent_id — the collection runs from an agent that can reach the target.
    • --host-inventory-once collects this host, prints the report as JSON and exits, contacting nothing. It is how an operator sees exactly what would be sent before enabling the schedule.

    Windows is reached by PowerShell over SSH, not WinRM. The intended client (github.com/masterzen/winrm) is Apache-2.0 itself and its graph carries no GPL or AGPL — but two MPL-2.0 modules and an ISC one, none on this project's MIT/Apache/BSD list, and it would add sixteen modules including a Kerberos stack to a cross-compiled agent to run one PowerShell command. Windows Server 2019+ ships OpenSSH Server, so transport: "ssh" reaches Windows too. "winrm" is a recognised-and-refused value whose error names the reason and the alternative.

    Posture, never key material. Certificate stores are read for certificates only: a PEM block that is not a CERTIFICATE is skipped before being decoded, and the stored shape has four fields — subject, issuer, SHA-256 fingerprint, expiry — with nowhere for key bytes to sit. The Windows script asks Get-ChildItem Cert:\LocalMachine\… for three properties rather than taking the certificate objects, which can carry a private key. A private key found loose in a trust directory is reported as a count and nothing else. No command transcripts, no process command lines, and no PID inside the durable socket fact. A fixture carrying a real private key appended to a certificate proves none of it reaches the report.

    Three-valued honesty throughout. Each section reports ok, failed or unsupported, and a failed section emits no fact — an absent fact means "not measured", where a fact with an empty value would mean "measured, and the answer is nothing". sw.package_count is emitted for an enumeration that genuinely found zero packages and never for one that failed. Hardware serial and UUID are absent rather than blank when DMI is unreadable, because a blank serial shared across an estate merges every host into one asset.

    A report too large to accept is its own answer. Intake refuses an over-cap submission with 413 naming the cap and what the agent declared it was sending, and the agent logs the size it actually measured and says plainly that waiting will not help — an over-cap report is the same size on the next run. Previously this and a malformed body both answered 400, so a host too big to report retried forever and never appeared in the inventory. The cap is derived from the collector's own ceilings rather than picked: at 20,000 packages and 1,500 trust-store certificates the worst legal submission is ~9.3 MiB, and the cap sits at 32 MiB, with a test pinning the relationship so the two cannot drift apart.

The held run is visible with an honest headline (materialized: 0, fully_materialized: false, and a line saying why) rather than absent, and the whole payload stays on the job row.

    • Ask the inventory a question and get back a query you can edit, plus the rows it selected. ADR-0008 D1's Query seam (shared/ai/ee/query), Enterprise, behind the provider boundary. This release ships the seam; the surfaces that call it — the MCP ask tool, the inventory endpoint and the command-palette mode — follow.

    The design is that a model never returns rows. It returns one line of the query language, which is parsed and validated against the catalogue, run by the read-only MCP tools under your own row-level security, and shown to you, editable. So an answer you disagree with is a predicate you can correct, and an answer you like is a view you can save.

    • It refuses rather than guesses. A query that does not validate gets one repair turn carrying the validator's own diagnostics, and is then refused with those diagnostics attached — "no field hostnaem on assets, did you mean hostname?" — instead of returning confidently wrong rows.
    • Every sentence cites a row, by asset id, and a sentence citing a row the model was not given is discarded. If nothing survives, the rows are still returned with a plain note saying the summary was discarded and why.
    • Nothing matched is not nothing is there. A query that selects no assets gets a fixed sentence saying exactly that, and the model is not asked to describe an absence it cannot cite.
    • Bounded, in code: two translation turns, three tool calls, three narration turns. After the rows are in, the model may ask for one of three read-only tools — asset detail, the class list, facet counts — and nothing else.

    • SBOM parsing: CycloneDX and SPDX documents into a normalised software model.     This is the parser library (workstream 2.6a). The upload endpoint, the Discovery → Sources page and the asset Software tab are 2.6b; nothing here is reachable by a user yet.

    • CycloneDX JSON 1.4–1.7 and SPDX JSON 2.2/2.3, detected from the document's own declaration rather than from a filename or Content-Type, neither of which is evidence. Product.Identity() is coalesce(purl, cpe, name || '@' || coalesce(version, '')) — including the inner coalesce, without which an unversioned product produces a NULL key and NULLs do not conflict, so every re-observation would insert another row. VersionSort() delegates to ast.VersionSortKey, the definition of version_sort and of the query language's version < 3.0; a second implementation would have the writer and the translator disagree silently.
    • Cryptographic components are skipped, with a counted warning. They are the CBOM path's business and an algorithm does not belong in a software catalogue. The fixture set includes the cbom-service formatter's own output, so a document this platform emits is one it accepts.
    • Nothing is silent. A malformed component, licence, edge or relationship is skipped with a warning rather than failing the document; a dropped purl or CPE names itself; a declared subject that cannot be read or resolves to no package says so rather than simply coming back absent; the two caps (32 MiB, 100,000 components) refuse the document rather than truncating it, because a half-ingested SBOM shows a software list that looks complete.     • No key material. redact.TextPEM runs over every string returned, warnings included — a warning quoting a malformed field is a leak path too, and it is the one nobody inspects. CERTIFICATE blocks survive: they are posture, and an over-strict scrubber is the same bug pointed the other way.

    • Existing retained observations that never produced an asset are automatically re-checked and materialized into provisional inventory items after upgrade, with no re-registration required. (#1898, #1901)
    • Automatic enrichment can refresh an explicitly configured source through a durable, deduplicated job, with tenant policy and executor checks and honest completion after ingestion. Admission and enrichment remain separately gated.

    • Inventory distinguishes unevaluated identity records from established and operator-confirmed identities, independently of approval and assessment.

    • "Stale" means one thing now: 30 days. The Inventory → Stale lens cut at 14 days while the Stale finding's first rung, the Inventory Hygiene control IH-004 and everything else that judges freshness started at 30 — so a record could be listed as stale with no finding, no failing control and nothing anywhere agreeing that it was. The lens now reads the same ladder the finding does, so it lists fewer records than before. Both sides come from one constant and a test fails if they part company again.

    • The hierarchical class facet — the dashboard's costliest query — is about nineteen times faster (243 ms → 13 ms on a seeded 50,000-asset tenant, identical rows). It counts the distinct class paths before expanding them into ancestor prefixes rather than after. The cost was never the work: the expansion itself was 76 ms, but generate_series(1, <expr>) carries no row estimate, so the planner costed the join at fifty million rows and crossed the JIT threshold — two thirds of the time went on compiling a plan for a query that touches 1,389 pages.

    • A class argued from a rule is now recorded as such. class_source_kind on an asset gained a fifth value, rule, alongside measured, declared, imported and inferred, and class_source_ref names the rule row. Calling a rule-derived class "measured" would claim we measured the mapping (we measured the MAC); calling it "inferred" would call a deterministic, citable rule a model. Both are false provenance on the one field used to audit a class.

    • The Approvals count and the Inventory banner include class proposals. Approvals is one queue, and a count that covered three of its four row kinds pointed at a page with more work on it than the number admitted.

    • proposed_by in the query language now finds rule-derived classes. The Inventory facet listed them and filtering on one returned nothing, because the predicate behind it named only the older machine-proposed kind. Filtering on a facet bucket and getting an empty page is a bug that reads as an answer.

    • An unknown host is now recognised by its serial number. "Unknown host" is the class for something in your own space that nothing has identified further — and, now, for a serial nothing has classified yet. A serial names one chassis globally, so two sightings carrying the same one are the same machine whatever either sighting managed to work out about it; withholding that from the least-identified class did not make it more honest, it made it unable to recognise something it had already seen. This affects every way assets arrive, not only the NetBox connector.

    Nothing about conflicting evidence changed: when a sighting's serial disagrees with the one an asset already carries — a restored image or a cloned machine carrying an agent's identity onto different hardware — you are still asked, in Discovery → Approvals, rather than told.

    • A host-inventory submission is about half the size it was. The package list used to be sent twice in every report — once in the collector's own record and once in the observations the platform materialises. It is now sent once, with the omission marked explicitly so an empty list cannot be misread as a host with no packages, and --host-inventory-once still prints the full local report. On a 20,000-package host the worst-case submission falls from ~9.3 MiB to ~5.1 MiB, against an unchanged 32 MiB cap.

    • An asset is a thing, not a listening port. The inventory's unit is now a configuration item with a class, identifiers and endpoints: a host exposing five services is ONE asset with five endpoints, where it used to be five assets. network_assets and devices are replaced by assets, asset_endpoints, asset_management and asset_credentials; the four-value asset_type enum is replaced by the class registry; and the address, port and identified service move from the asset to the endpoint. What that removes, and why nothing is carried forward, is under Removed below. Phase 1 of the general asset inventory initiative (ADR-0002, ADR-0007); no public release is cut until core-v1.0.0.

Sensor ingest, active scan, cloud discovery, PCAP, spreadsheet import, CMDB pull and manual create all build an observation and resolve it through shared/identity instead of the four different dedupe keys they used before (manual create did not dedupe at all). A hostname or an IP now identifies only within its network SEGMENT, a serial or a cloud resource id identifies globally, and identifiers that resolve to more than one asset open a merge proposal in Approvals rather than merging anything.

    • Asset risk can go down. The per-asset score is recomputed as the maximum over the asset's scored crypto configurations. The previous write was GREATEST(old, new), so removing the last weak configuration left the asset reporting its old maximum forever. risk_assessed_by records which producers have looked, so a score of 0 with an empty array (not assessed) is distinguishable from 0 with {crypto} (assessed clean).

The MCP vistaplatform_get_control_findings tool description changed with it.

NULL means "drawn before this column existed" and is deliberately distinct from declared — a segment somebody drew two years ago has no recorded provenance, and labelling it would invent a fact. A NetBox prefix that matches an existing segment stamps the provenance and leaves the tenant's name, environment, tags and auto-approval settings alone.

    • Two unused search indexes on the findings table are gone. They were trigram indexes meant to speed up the Findings page's free-text search, and Postgres could never use them: the search matches a term against the summary, the subject label, the finding kind OR the host, and a disjunction that includes the host lookup cannot be served from an index at all.     The two were written by different statements in different transactions — the column by ingest, the junction row by a later best-effort call that only logged on failure — so they could diverge, and did: the original valid_certificate_role CHECK rejected the literal leaf, so on every sensor-discovered certificate the column landed, the junction insert was refused, and ingest reported success. The certificate existed and carried its risk while being unreachable from, and unsearchable by, the asset it was served on.

    Ingest now writes both halves in one transaction, deriving the junction row from the row's own certificate_id so the two cannot name different certificates, on both the insert and the re-observation path. Configurations written before that — and the demo/QA fixtures that set only the column — are converged by an idempotent backfill in the schema's POST-MIGRATIONS block, so an existing database repairs itself on the next apply.

The append now runs in a SAVEPOINT, so "best-effort" is a property of the code rather than a comment above it.

It wrote a "default compliance framework" key into the shared tenant settings document that no code anywhere read back — the authoritative default framework has lived on the tenant's framework licences in compliance-engine since the evaluation rework. Existing stored values are left in place, unread; the GET no longer returns the field and the PUT no longer accepts it.

    • The MSP tenant-settings save no longer wipes a tenant's other settings. admin-service's MSP PUT .../tenants/:id/settings replaced the entire tenant_admin_settings.config document with just the fields the MSP form itself owns (frameworkId, email_verification_required, onboarding_required) — so a platform admin saving any one of those silently deleted the tenant's discovery_auto_scan policy, drift baseline window and identity auto-accept threshold, each owned and written by a different service. The audit trigger recorded the wipe but nothing prevented it. The save is now a top-level jsonb merge (config || EXCLUDED.config) that only ever touches the keys the request actually sets — an absent field leaves the stored value untouched rather than nulling it out. See services/admin-service/ee/msp/tenant_settings.go.

    • cluster-sensor-service could not read back a discovery job the platform created on its own initiative (created_by IS NULL — every HMAC service-auth caller, including the automatic active-scan sweep), nor one that named a sensor, nor list jobs at all, so such jobs would have sat in queued forever with the stuck-job sweep republishing them to the same failure every 30 seconds. All three reads are fixed. (#1839)

    • Risk, cryptographic strength, compliance, health and confidence now retain their own units and shared definitions. Crypto findings inspect every relevant component instead of treating a high catalogue score as proof of weakness; unscored CVEs and unresolved evidence remain visible. Compliance/hygiene colours retain their existing thresholds. External strengths use a nullable canonical vocabulary with preserved historical values, control writes use lowercase severities, and new catalogue rows require explicit scores. See the rating upgrade guide for coordinated schema/client changes, reassessment and evidence limitations.

    • A denied asset's last-seen no longer freezes the moment it is denied. Re-observation ingest hard-filtered a denied asset BEFORE the observation ever reached the identification engine, so its last_seen_at (and every operational surface ordered by it) never moved again however many times a sensor kept reporting it — even though the same re-observation correctly keeps archived assets' last-seen current. A denied asset still stays denied and its crypto is still never (re-)materialized; it now also still advances its last-seen, via a minimal touch that deliberately does not run the full identity resolve — a denied asset gains no new identifiers, no new endpoints and no reclassified ownership, only the honest fact that it is still being seen.

    • sensor_discoveries.approval_status no longer says "pending" forever on rows no human will ever act on. Two classes of processed row sat pending indefinitely: host observations (identity evidence, never a crypto finding awaiting approval) and findings that matched an asset already archived or denied (nothing is materialized for either, and no approval decision follows). Both now land on a terminal value — observed and suppressed respectively — set at write time going forward and backfilled for existing rows on upgrade. cluster-sensor-service's per-job materialization summary no longer counts either as "awaiting approval" (previously approval_status <> 'auto_approved', now = 'pending'), and the Discover wizard states suppressed findings ("N on denied or archived assets — not shown in Approvals") instead of silently folding them into "awaiting approval" or a shortfall nobody could explain.

    • Reverse-DNS hostname resolution for a sensor discovery now only runs against a public destination address. For a private/LAN address the cluster's own resolver is either unreachable for that address or answers a different network's idea of it — and is weaker evidence than the sensor's own passive mDNS/NBNS/LLDP observations besides, for exactly the population (LAN hosts) this affected most. The fabricated-cluster-answer rejection (#1804) is unchanged and still applies to the public case; sensor-side passive DNS capture is a separate code path and is unaffected.

    • A partially observed crypto configuration is now completed by the full observation instead of sitting beside it. A passive sensor that decodes only the protocol of a handshake wrote a configuration with every component empty; the active probe that followed measured the full handshake and, because the two fingerprints differed, added a second configuration for the same endpoint that never superseded the first. The asset page listed both, the inventory's configuration count included both, and the CBOM shipped an empty component beside the real one. Ingest now recognises a live configuration whose measured components all agree with a fuller observation as the same configuration seen less completely, fills it in place (keeping its first-seen date, certificate and links) and re-scores it exactly as a fresh one; a less complete re-observation of a configuration already held is treated as a re-observation, never a new row. A genuinely conflicting pair — TLS 1.2 seen passively, TLS 1.3 seen actively — stays two configurations. Each configuration now records every discovery method that contributed to it (discovery_methods, shown as provenance chips on the asset page's Cryptography tab), and the schema reconciles pairs written before this fix on upgrade: the partial row is retired (soft-deleted), its certificate and algorithm links and tickets move to the complete row, and the complete row inherits the earlier first-seen date.

    • A floating address no longer proposes merging the service at it with the node announcing it. MetalLB in L2 mode, kube-vip, keepalived, Windows NLB, VRRP, HSRP and CARP all announce a virtual address by gratuitous ARP from whichever node currently holds it. The sensor decoded that correctly — the node's MAC at the floating address — and the identification engine, finding the MAC on the node's asset and the address on the service's, called it a cross-kind conflict and opened a merge proposal (scored 0.84, because a MAC is a strong identifier), again after every "keep separate". Three changes, one rule each: (1) an observation that is only a measured MAC-to-address binding — no name, host key, serial, agent or cloud id — whose MAC and address resolve to two different assets is now resolved to the address's asset with the MAC deliberately left unattached, recorded as a hosted_on relationship (service → node) carrying the evidence, and opens no proposal; an observation carrying the node's MAC plus a name or stronger identifier of the other asset is still the genuine conflict it always was. (2) A reviewer's "keep separate" is now read back: a conflict between assets a reviewer already kept apart, on the same kinds of evidence, is resolved without re-asking (to the earlier proposal's own observation asset when it had one, otherwise to the asset the weaker evidence names), the history entry names the honoured proposal, and the ingest log says "kept separate on "; new evidence of a kind the reviewer never saw reopens the question. A question already pending is also no longer re-noted in history on every observation that re-asks it. (3) VRRP/CARP (00:00:5e:00:01:xx, 00:00:5e:00:02:xx), HSRP (00:00:0c:07:ac:xx, 00:00:0c:9f:fx:xx) and GLBP (00:07:b4:xx:xx:xx) virtual router MACs — which move between routers with the address — are no longer used as identifiers, like locally-administered MACs; the protocol is kept as an attribute.
    • MCP OAuth discovery now points somewhere. The MCP endpoint's 401 answered WWW-Authenticate: Bearer resource_metadata="" — an empty pointer, from which a client learns nothing and abandons the flow — and /.well-known/oauth-protected-resource was not routed at all, so it fell through to the web-UI catch-all and returned the app's index.html with HTTP
    • A client following the chain received HTML where it expects JSON, with a success status hiding it. mcp-service now serves RFC 9728 protected-resource metadata at both the well-known root and the RFC 9728 §3.1 path-suffixed URI, the chart routes those paths to it ahead of the UI catch-all, and the 401 carries the document's absolute URL. Note this is necessary but not sufficient for hosted clients: Vista's authorization server still does not implement RFC 7591 dynamic client registration, so Claude.ai, ChatGPT and Claude Code cannot complete automatic sign-in and must use a Personal Access Token.
    • The sensor's heartbeat now reports config_running — the effective values of every control-plane-managed setting (active_probing, network_discovery, host_observation, host_observation_window_seconds, host_observation_dns, dedup_ttl_minutes, reporting_interval_seconds, log_level) seeded from its own configuration file. Without it, sensor-manager's platform bootstrap had nothing to adopt on a sensor's first report, so a sensor with locally customised settings would be silently reset to built-in defaults on its next beat.
    • An agent's first heartbeat no longer switches off what its configuration file turned on. Control-plane-managed settings (#1785) resolved to their built-in defaults for any device nobody had configured, so an agent started with HOST_INVENTORY_ENABLED=true was handed false about a minute later and stopped collecting for good; poll and heartbeat cadences reset the same way. A device now reports the settings it is running, and the first report — that one only — is adopted as its own override where nothing else is set and the value differs from the built-in default. The revision it receives therefore describes what it is already doing, an operator sees the real starting position in the console instead of a default nobody chose, and a device running the defaults still inherits any fleet default set later. Recorded in the audit trail under its own bootstrap scope with no acting user, because nobody made the change.
    • External connections no longer count certificate-hygiene observations (a missing Signed Certificate Timestamp, an untrusted or self-issued/pinned CA, an incomplete chain, a missing Subject DN) as cryptographic weakness. A TLS 1.3 / AES-256-GCM connection to a trusted endpoint could previously be flagged "weak crypto" on the dashboard's External Exposure panel for no reason other than a missing SCT. Those observations are now recorded separately (cert_hygiene_flags) instead of folding into weak_reasons/ crypto_strength. Also extends Signed Certificate Timestamp detection to all three RFC 6962 delivery routes (embedded, TLS extension, OCSP) via a new cert_sct_source field on both external_connections and certificates, where previously only the embedded route was checked.

    • Actively probed SSH servers now report their key exchange, cipher, MAC and host-key algorithms. The active probe completed a key exchange with a library that exposes no algorithm names, so an SSH crypto configuration reached the inventory with only a banner and a host key type: key_exchange_algorithm, symmetric_encryption and hash_algorithm stayed NULL, nothing resolved against the algorithm catalogue, and every SSH asset scored 0 — which the product means as "not assessed" — however it was configured. The shared prober now reads the server's SSH_MSG_KEXINIT in cleartext before any key exchange, records the offered name-lists verbatim and derives the negotiated algorithm per RFC 4253 §7.1. Weak offers (diffie-hellman-group1-sha1, CBC and 3DES ciphers, hmac-md5, SHA-1 ssh-rsa host keys) are linked as inferred, so worst-component-wins scoring reports what a server will agree to rather than only what it agreed with us. Reading KEXINIT needs no algorithm in common, so a legacy-only appliance — previously reduced to a banner — is now inventoried in full. The standalone sensor and the in-cluster Platform Sensor share the probe and both carry the result.

    • SSH banners no longer carry a binary packet. The banner-only fallback read a fixed-size blob rather than the identification line, and an SSH server sends its SSH_MSG_KEXINIT immediately behind that line — usually in the same TCP segment — so algorithm name-lists, a cookie and random padding were stored as the device's banner and shown in the UI. The read now stops at the line terminator RFC 4253 §4.2 defines.

    • Algorithm catalogue: five SSH names a current sshd offers. Added sntrup761x25519-sha512 (the standardised spelling OpenSSH offers from 9.9), mlkem768nistp256-sha256 (post-quantum hybrid, flagged is_pqc), curve448-sha512, hmac-sha1-96-etm@openssh.com and hmac-md5-etm@openssh.com. Without a catalogue row these resolved to nothing and the component was recorded as unassessed.

    • An active-scan target that was an IP literal duplicated the endpoint. When an intake path did not know a listener's name it could write the scan target into fqdn even when the target was an address — it has dots, so it passed a naive "contains a dot" check — producing a second asset_endpoints row for a listener already recorded with fqdn NULL, each with its own crypto configuration and findings. An IP is never a name: it is now dropped from fqdn at the source (the active-scan finding builder) and at the funnel (identity.EndpointObservation.Sanitized), and an address-bearing endpoint is now matched on (address, port, transport) rather than the full tuple including fqdn, so a differently-named re-observation of the same listener updates the existing row instead of inserting a second one. Existing duplicate rows on upgraded installs are merged by a one-time reconcile, keeping the oldest row and re-pointing its crypto configurations, external connections and SSH keys. The reconcile never keeps an IP literal as the survivor's name: the losing rows the defect wrote usually hold the address spelled as text, so backfilling one would have re-created the very value this release stops writing — permanently, because a name is only ever filled onto a row that has none. A real name among the duplicates wins, a survivor carrying the literal itself is corrected, and a lone row that has only the literal is cleared.
    • discovery-processor-service's reverse-DNS enrichment ran from inside a cluster pod, whose resolver synthesises PTR answers for in-cluster IPs (<a>-<b>-<c>-<d>.<namespace>.svc.cluster.local and similar) — a customer host's real address could come back as a Kubernetes-internal name nothing on the customer's network ever answers to. reverseDNSLookup now rejects cluster-internal answers and returns "" instead, so the asset keeps its address as its display name until a real name arrives.
    • Several device-interrogation collectors (UniFi managed devices and VPN networks, Fortinet IPSec tunnels and SSL VPN, PAN-OS SSL-decrypt profiles and security rules, F5 virtual servers, SNMP sysName) copied a vendor display/config label straight into the asset's hostname field. A label like "U6+ Living Room" or "Back Porch #1" is not a DNS name, so the identity layer rejected it as an invalid hostname identifier on every run — losing the identifier and flooding the log with the same reject. Collectors now keep the raw label in asset metadata for display and only promote it to hostname when it is a valid DNS name.
    • Third-party TLS connections with no reverse-DNS record (most cloud/CDN IPs) now show the hostname the client's TLS ClientHello actually requested (SNI) instead of a bare IP:port in Inventory → 3rd Party — sensor-manager and discovery-processor now fall back to the captured SNI before reverse DNS, and external_connections.dest_hostname fills from a later observation without ever being blanked by one that carries no hostname.
    • Ingest now defers a finding's certificates and crypto configuration on the status the matched asset has, not the one the batch asked for. A discovery row that matched no auto-approval rule — the same host seen on an address in no registered segment, a TLS endpoint reported by device interrogation — arrives pending_approval, and when it landed on an asset already monitoring its crypto was parked in assets.metadata->'deferred_findings', which only an approval of a pending asset ever replays. It is materialized immediately instead, and the import response reports the effective status per finding so discovery-processor stamps those sensor_discoveries rows auto_approved rather than leaving them pending where nothing surfaces them.
    • A discovery no longer un-archives an asset. A device the tenant archived and that later reappeared on a segment carrying an auto-approval rule was promoted back to monitoring — with an approved history entry naming no person — and its certificates and crypto configuration written into the live inventory. Archiving is now respected the way denied always was: the status is left alone and the finding is neither materialized nor deferred.
    • Sensor heartbeat discoveries_made and errors_count were not trustworthy. discoveries_made read the length of the in-memory batch buffer, which drains every report interval — a sensor that had accepted hundreds of discoveries over its lifetime reported discoveries_made: 0 on every heartbeat after its first successful submission, making an active sensor look idle on the sensor detail drawer. errors_count was hardcoded to 0. Both are now cumulative, process-lifetime counters: discoveries_made increments when a discovery is accepted into a submit batch (not on successful upload, so outages don't hide capture activity), and errors_count increments at the sensor's existing capture/submission/heartbeat/registration failure log sites.
    • Reflected mDNS no longer inventories the gateway as every host on every other VLAN. The sensor attributed every mDNS response to the frame's sender MAC, and a router running an mDNS reflector (UniFi, Avahi, Bonjour gateways) re-originates other hosts' announcements from its own MAC. A response now counts as the sender's only when an A/AAAA record names the frame's source address; otherwise it is hearsay about the named host, carries no MAC, and is graded like a DNS answer. The consumer files .local names as segment-scoped hostnames rather than globally unique FQDNs, so a reflected copy of a name can no longer absorb the host itself from another segment.
    • A platform-sensor scan that asked for TLS and SSH no longer records "SSH on 443" with TLS data. A finding created for one requested protocol only receives that protocol's probe, and a protocol refuted by its own probe on a port it is not known on records no finding instead of an empty crypto configuration.
    • A host inventory the platform could not materialise no longer reads as a success. The Job Logs line leads with the consumer's error instead of the listener count it never wrote, and the agent card's "Last host inventory" ignores failed runs.
    • A name typed on the Devices page is now the asset's display label. Registering a device that the sensor had already observed kept the sensor's measured name as the label; the declared name now wins, while an address typed into the same field still only fills an empty label.

    Removed¶

    • measurement_types.extraction_query (asset-inventory workstream 3.6, ADR-0005 D5). The column stored the SQL a measurement type "runs". Nothing ever executed it, and what a measurement type reads is now declared in standards/measurement-types.yaml. A seeded query is an injection hazard and an upgrade hazard at once, and a column holding SQL that nothing runs is a standing invitation for something to start running it. Dropped from the schema, the API and the generated client.

    • compliance_findings is dropped. There is one findings table, and every producer writes to it. Asset-inventory workstream 3.1 (ADR-0005 D3): the compliance producer's rows now carry producer = 'compliance' and kind = 'control_noncompliant' in the unified table alongside the crypto, end-of-life, vulnerability, configuration, hygiene and drift producers that follow it. No view, no backfill, no dual-write — ADR-0007's no-migration decision applies, the old table is dropped in POST-MIGRATIONS with DROP TABLE IF EXISTS ... CASCADE, and scripts/audit-removed-tables.mjs fails make audit on any Go or SQL that still names it.

    What changed in the shape, and why each one had to:

    • Subject, not asset. (asset_id, asset_type) and its three-value CHECK become (subject_id, subject_type) from the registry's vocabulary, and the three values map onto two: network_asset → asset, crypto_implementation → asset, certificate → certificate. The old asset_type named the measurement KIND, not the type of the id beside it — asset_id was always the asset's for the first two, because a cryptographic configuration measurement is scoped and selected per asset. On live data about three in four of those ids were a certificate's, which is why the old name described the minority case, why the posture grid dropped three findings in four into an "unattributed" row, and why a certificate finding rendered a raw UUID where a hostname belonged.

      The configurations a measurement was taken over are not lost: they are listed on the finding as evidence.crypto_implementation_ids, which is what the inspector links through and what a ticket copies into crypto_implementation_id when there is exactly one. crypto_configuration remains a valid finding subject, reserved for the configuration producer that measures one at a time. - Severity is the registry's lowercase ladder (info/low/medium/ high/critical), not Low/Med/High/Critical. Med had no spelling anything else in the product used. Control authors still type High, so the writer normalizes and the database holds one vocabulary. - Identity gained control_id, with NULLS NOT DISTINCT: a compliance finding is one per (control, subject) pair, so two controls failing on one server are two things to triage. Without it the second control's write reaches the first's row through ON CONFLICT and overwrites it — a lost violation with no error. NULLS NOT DISTINCT keeps the dedup on for the six producers that leave control_id NULL, which Postgres would otherwise treat as always-distinct. - The workflow columns came with it — assignment, remediation notes, resurfaced-at, staleness. None is compliance-shaped; they are the finding LIFECYCLE, which is the half of the old table that generalised. - compliance_finding_history, remediation_plan_items and tickets keep their finding_id, re-pointed at findings(id). A ticket whose finding is gone survives with the link cleared, because the ticket is the user's work.

    • The port-as-asset tables, and the asset_type enum, are dropped — with no migration and no compatibility view. network_assets (the view, the partitioned parent and its eight partitions), devices, and the four-value asset_type enum are removed from the schema body and dropped in POST-MIGRATIONS with DROP TABLE / DROP TYPE IF EXISTS ... CASCADE. Links are re-parented rather than bridged: crypto_implementations.endpoint_id, external_connections.source_endpoint_id and ssh_keys.endpoint_id now point at the endpoint, while device_jobs and database_encryption_states point at the asset.

    The owner established (2026-09-11) that there are no installs of the current line to carry forward — the public repository has no released version on this model, and our own development cluster is rebuilt from the published chart — so a compatibility view would have been a layer maintained for nobody, and every reader was rewritten in place instead. make audit runs scripts/audit-removed-tables.mjs --strict unconditionally so a query naming one of these cannot reach main: a dropped relation does not fail to build, it fails at runtime, per query, and this codebase has form for swallowing exactly that error behind a 200.

    The scopes and auto-approval-rule JSON predicate columns go the same way, replaced by a query text column holding a query-language string.

    • The legacy per-field asset filters are gone from the MCP tool surface, with no deprecation window: query_assets takes a query string, and sending one of the old filters is a schema violation refused before any backend call. The REST API keeps them for one release, translated into the language server-side.

    • GET and PUT /api/v1/inventory-service/discovery/capabilities (and their /api/v2 twins), together with the capability_policy key they wrote into tenant settings. They served the retired web-ui discovery wizard; no current UI, MCP tool or QA tool called them, and no discovery path enforced the key. The two real switches are unchanged: Settings → Discovery → Active Scanning for automatic scans, and the per-job active_scanning option a discovery job carries. The MSP tenant-settings endpoints in admin-service no longer echo or accept capability_policy.

    Security¶

    • npm: uuid pinned to ≥ 11.1.1 through a root overrides entry (GHSA-w5hq-g745-h8pq, missing buffer bounds check in v3/v5/v6). It reaches the tree only as exceljs's dependency and exceljs calls v4 without a buffer, so shipped behaviour is unchanged; the lockfile no longer carries the vulnerable version.

    • The AI provider transport followed a redirect off its own origin, re-sending the prompt. A model endpoint that is compromised, misconfigured, or reached through a poisoned resolver could answer 307/308 with a Location anywhere; Go re-sends the POST body, so the whole prompt — system prompt, question, and the grounding rows the redaction boundary had just decided were safe to send to THAT provider — was delivered to a host the endpoint chose, with the call still succeeding. Under AI_ALLOW_PRIVATE_ENDPOINTS (a self-hosted model, the flag's whole purpose) the client has no dial guard at all, so the target could be the cloud metadata endpoint. The transport now refuses any redirect that leaves the configured endpoint's scheme+host, the same decision the NetBox connector already made for itself; a same-origin redirect is still followed, because a reverse proxy normalising a path is legitimate.

    • Every upload cap in the platform was preceded by an unbounded read. The audit middleware, which runs ahead of every handler in all sixteen services, read each request body into a buffer and never used the bytes. The SBOM upload's 32 MiB ceiling and the host-inventory intake's were therefore applied to a body that was already resident, so an authenticated caller ignoring them could make any service hold whatever the edge forwards, per concurrent request, before a handler line ran. The read is gone; both caps now bind.

    • POST /ask and POST …/draft-controls decoded unbounded bodies before applying their published caps. Both checked their limit — 4096 characters for a question, 64 KiB for a pasted standard — on a string the JSON decoder had already built, so the cap chose which error the caller got and said nothing about the allocation. Both now bound the body first and answer 413 naming the published cap, with headroom for JSON escaping so a legal request never meets the transport bound. The drafting endpoint's published 64 KiB cap was also a property of one Author implementation rather than of the endpoint — it lived inside the Enterprise drafter, so any other seam (the null one, a future local model) received whatever got past the transport bound, eight times the number the error message names. It is now checked at the seam, before dispatch.

    • passcode and a bare pin are credentials the redactor did not recognise. Neither matched a fragment nor ended in "key". Added, with snmp_version, pinning and pinned_certificate pinned as must-survive so the fix cannot become the over-strict version of the same bug. (This finding also covered SNMP community strings, which gate 4 closed independently and better, with a suffix rule rather than the bare fragment X.5 proposed — communityGalleryImageId is an Azure image id and is posture.)

    • The resource-tracking middleware drained every request body too, so the fix above did not bind. Six services — auth, admin, cbom, compliance-engine, inventory-service and sensor-manager — register resourcetracking.Middleware BEFORE the audit middleware, and it read each body into a buffer for the same stated reason and threw the bytes away the same way. Removing the audit read alone therefore changed nothing for the SBOM upload's 32 MiB cap, the catalogue bundle's, /ask's or draft-controls'. It now counts the bytes the handler reads through a transparent wrapper instead of buffering them, so the usage meter reports the same number and every downstream MaxBytesReader finally binds.

    • Two settings on one page asked for two different permissions. PUT /settings/identification (the auto-merge threshold) was gated on assets.update while its sibling card on the same Settings page, the drift baseline, was gated on settings.update — so a role granted one and not the other could edit half a page, with nothing on screen saying why. The threshold now requires both: settings.update because it is a settings page, and assets.update because the threshold authorises the platform to merge two of your assets without asking, which is the same act as accepting a merge proposal by hand. Swapping one for the other would have let settings.update alone authorise asset rewriting.

    • Owner email addresses no longer cross the AI provider boundary. owner_email was on the allowlist of asset-row fields sent to a model for the narration turn. The redactor does not touch it — an address is not secret-shaped — so the allowlist WAS the decision, and it was one a field list implied rather than stated. It is projected out, and the ai-assistant page now says in so many words what an asset row carries when it is sent. The capability is unaffected: exists(owner_email) is a predicate and runs in Postgres, so "which production servers have no owner?" is still answered — what the model no longer sees is the address it could only have repeated back.

    • Accepting a drafted remediation plan now records the server's provenance, and bounds the plan. POST /findings/:id/remediation/accept stamped the row inferred with a source_ref built from the model id in the REQUEST BODY, so the one piece of provenance the server could have stood behind was a caller assertion — any client could claim any model, of any length. The row now names the model this deployment is configured with, or remediator:model when it pins none. steps and summary were also unbounded, and are rendered into the plan item's notes; they are now held to the same limits that bound what the drafter may propose (12 steps, 600 characters each), refused rather than truncated. A plan this platform drafted always fits.

    • A human's decision on a merge, class or relationship proposal is now audited by name. The accept and reject routes carried no explicit audit entry, so the record said "POST /approvals/classes//accept, 200" and not which class was applied to which asset. Note the asymmetry that made it worth closing: the MACHINE path (an auto-accepted merge) writes a rich record — score, model, candidates, reason — precisely because nobody is there to ask, while the path with a person behind it wrote less.

    • Three audit events in this build were being discarded by the database. audit.activity_logs.event_category carries a CHECK constraint, and data_modification (the auto-accepted merge) and configuration (both tenant settings handlers, and the algorithm-catalogue writes) are not in it — so every one of those entries was rejected on INSERT with nothing visible to the caller: the helper discards the error, the write is batched, and the flush is a background goroutine talking to another service. Two of the shared audit package's own published category constants were values the database rejects, which is where configuration came from. The constants are corrected, the call sites use them, LogActivity now refuses an unstorable category loudly instead of letting it vanish, and two tests hold the line: one derives the valid set from the CHECK in schema.sql, the other scans inventory-service's own call sites.

    • A statement ceiling on every read that runs a tenant's own query. The asset list, the facet rail and the stale list splice a caller's query-language predicate into their WHERE clause, and no deployment set a statement_timeout; context cancellation was the only backstop, which sends a cancel request on a second connection and leaves the statement running until the backend notices. Those reads now open their transaction with SET LOCAL statement_timeout, five seconds, reverting with the transaction so it cannot leak onto a pooled connection.

    Honest about what prompted it: the review expected a catastrophic regex ((a+)+) to be the way in, and that was measured and does not reproduce — PostgreSQL's ARE is a hybrid DFA and returned in under a millisecond on every pattern tried. The ceiling is kept as a general bound on a predicate a tenant controls, not as a fix for a demonstrated blow-up, and the tests say so.

    • The findings evidence rail has a redaction backstop. Writer.Upsert wrote Finding.Evidence verbatim into findings.evidence, a jsonb the UI renders and the remediation drafter reads, for every producer. Every other rail in the platform has a backstop and this one — the single chokepoint for six producers — had none. Nothing leaks through it today; the point is the next producer. A key the redactor has explicitly NAMED as a credential is now masked, and PEM private-key blocks are masked inside string values wherever they appear. Deliberately NOT the ordinary redactor: its catch-all treats anything ending in "key" as material, and the drift producer's observation_key is the finding's own identity. Masking that would have broken a producer silently, which is the same bug pointed the other way.

    These twelve come from the general asset inventory's cross-cutting security review (BUILD_PLAN X.5), whose full findings — including what was reported for the owner rather than fixed — are in docsv4/internal/developer/design/asset-inventory/SECURITY_REVIEW_X5.md.

    • The parallel DB-integration test run is deterministic again. Nightly test-backend failed on two consecutive nights and roughly half of local make test-integration-db runs failed, always in a different test, always one that passed alone. The cause was not any of those tests: shared/testdb's ~200 ApplySchemaAndSeed call sites each re-applied the whole 30,000-line schema.sql and seed.sql from inside a run whose package binaries are parallel, so an apply held ACCESS EXCLUSIVE across every table while other packages were mid-transaction and Postgres broke the cycle by killing one side (40P01 deadlock detected). The seed half had the mirror problem — its tenant-scoped inserts select from tenants, and a throwaway tenant being CASCADE-deleted mid-statement failed their foreign-key check, exhausting the applier's retries and failing a whole package at setup.

    Both files are now applied once per database: their sha256 is recorded in testdb_meta.applied_sql by the local runner and by nightly, and the harness reads that marker while holding the same exclusive advisory lock the apply takes, so two binaries cannot both decide to apply. A test whose subject is the re-apply calls the new testdb.ForceApplySchema / ForceApplySeed. The role and grant re-assertions behind ConnectAsAppRole (a GRANT … ON ALL TABLES per call, which rewrites a pg_class row per table) are cached the same way. Ten consecutive full parallel runs are clean, with zero genuine transient-race retries where the same tree previously logged fourteen.

    Locking the tenant lifecycle against the applier — the other obvious fix for the seed half — was tried and reverted: it hangs the suite, because a shared advisory request queues behind a waiting exclusive one, so a test holding a row lock and then wanting a tenant waits on an applier waiting on that row lock. Ten packages sat at the timeout under nightly's own whole-module command. The seed re-applies simply stop happening instead, which leaves the two deliberate re-appliers to the foreign-key retry that exists for them. NewTenant carries a comment saying not to try it again.
