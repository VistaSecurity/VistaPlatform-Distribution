    Releases & Versioning¶

    How Vista Platform Core releases are versioned, where they are published, what they contain, and how to verify them.

    What changed after 5.2.1. The platform's source code is no longer published. Core stays free and is distributed as signed container images and a signed Helm chart, with its install files, verification instructions and issue tracker in the public Distribution repository. The sensor and the device interrogation agent are open source under the Apache License 2.0 in the Agents repository. Download links in consoles of 5.2.1 and earlier stop working, with no redirect: see the dated notice of 2026-10-28.

    Versioning¶

    Releases follow Semantic Versioning (vMAJOR.MINOR.PATCH). For any given release the version is identical across:

    • the release on the Distribution repository (e.g. v5.3.0),
    • the Helm chart version and appVersion (5.3.0), and
    • every service container image tag (v5.3.0).

    So a chart at 5.3.0 always runs the v5.3.0 images; there is no skew to reason about. Core publishes final releases only: there are no release-candidate tags.

    What a release contains¶

    Each release is published as signed, attested artifacts on GHCR, plus a set of release files:

    • The Helm chart: oci://ghcr.io/vistasecurity/vistaplatform:<version>. It pins every image by digest, and carries a cosign signature, a CycloneDX SBOM attestation and an in-toto release manifest that lists every image.
    • Service images: ghcr.io/vistasecurity/<image>:v<version>, each cosign-signed (keyless) with a CycloneDX SBOM attached as a signed attestation. They are compiled from source that is not published, and the Go services are obfuscated. Each image carries the Vista Platform License, TERMS.md and its own third-party notices under /usr/share/doc/vista/, and names its licence in its OCI labels.
    • Release files on the Distribution repository's release v<version>: compose.yaml and env.example (the one-host install, every image pinned by digest), values-core.example.yaml (a starting values file for the chart), IMAGES.txt, VERIFY.md, AGENTS.md, feature-status.json, the operator tools bundle-decrypt-<os>-<arch> and catalog-bundle-<os>-<arch> for Linux, macOS and Windows, and a signed SHA256SUMS over all of them.

    A release does not carry sensor or device-agent binaries. The agents are released by the Agents repository; AGENTS.md names the agents release this platform version was tested with, and the console offers exactly that release (Discovery → Sensors & Agents).

    Install and upgrade from the published chart or the release's compose.yaml. Neither needs the source code or a local build.

    Release notes¶

    • Per-release page: every release has a page under Release notes on this site, and the admin console's Maintenance → About & Updates links the page of the version it offers.
    • Distribution release: the release v<version> on the Distribution repository carries the install files above and a short note.

    Verify a release¶

    Signing is keyless: there is no key to trust, because the signing identity is the release workflow. Use the command helm install printed at the end of its output, or the release's VERIFY.md: both name the registry, the version and the signing identity for the artifact you actually have.

    For Core releases after 5.2.1, the identity is the release workflow run from the tag core-v<version>:

    cosign verify ghcr.io/vistasecurity/vistaplatform:<chart-version> \
  --certificate-identity-regexp '^https://github\.com/VistaSecurity/VistaPlatform/\.github/workflows/release-core\.yml@refs/tags/core-v[0-9]+\.[0-9]+\.[0-9]+$' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

    Substitute a service image ref (e.g. ghcr.io/vistasecurity/auth-service:v<version>) to verify an image with the same identity, and read its SBOM with cosign verify-attestation --type cyclonedx, as VERIFY.md shows. The platform's release workflow lives in a private repository; its identity is still a plain string the certificate carries, and the public Rekor transparency log records every signature it made.

    Releases up to and including 5.2.1 were signed by the release workflow of the former public source repository, and verify with --certificate-identity-regexp '^https://github\.com/VistaSecurity/VistaPlatform-Core/\.github/workflows/release-core\.yml@refs/tags/v[0-9]+\.[0-9]+\.[0-9]+(-[A-Za-z0-9.]+)?$'. They keep the licence they were published under, FSL-1.1-ALv2; nothing in a later release changes it.

    The agents have their own signing identities, in the Agents repository's Verifying a release.

    Upgrading¶

    The usual way is the admin console: Maintenance → Backups to take a backup, then Maintenance → About & Updates to see what's new and update. See Maintenance in the admin console. The manual procedure below is for installs managed by Argo CD or Flux and the fallback.

    See the "Upgrade" sections of INSTALL.md (Docker Compose) and of the Helm guide for cross-version upgrade mechanics (--reset-then-reuse-values, schema-migration/seed Jobs, single-node surge caveats). The chart's NOTES.txt echoes the key upgrade flags on every helm upgrade.

    Bundled NATS server: 2.10 to 2.14¶

    This release upgrades the NATS server bundled with the chart (datastores.nats) from 2.10, which the NATS project no longer patches, to 2.14.

    • JetStream data is preserved. Streams, durable consumers, their acknowledgement state and stored messages are read in place from the existing volume. Nothing needs to be re-created.
    • Rolling the chart back is not clean. If you later roll back to a release that ships NATS 2.10, the server rebuilds the stream index on its first start and logs Filestore [<stream>] Recovering stream state from index errored: corrupt state file. The messages and consumer state were intact in testing, but the rebuild is expected, not a fault.
    • Take a backup of the NATS volume before upgrading if you need a clean rollback. The bundled server stores its data on the PVC named nats-data-nats-0; snapshot it with your CSI driver or storage layer.
    • A pinned tag keeps the old server. If your values file sets datastores.nats.image.tag, that value wins over the chart default, so remove it (or set it to 2.14-alpine) to take this change. Use --reset-then-reuse-values as described above. If you run an external NATS (datastores.nats.enabled: false), nothing changes for you; keep it on a release line the NATS project still patches.

    1.0.0 is a fresh install only — there is no upgrade path from a core-v0.x release. See the 1.0.0 release notes before upgrading an existing deployment: the port-as-asset tables were dropped rather than migrated, and credential encryption moved to v2, so credentials need re-entering and sensors re-enrolling on the first 1.0.0 deploy.
