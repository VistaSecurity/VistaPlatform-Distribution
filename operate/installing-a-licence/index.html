    Installing and renewing a licence¶

    A Vista Platform licence is a signed token from Vista Security. It makes an install Starter, Pro, Enterprise or MSP until the date it expires, and it can carry exceptions or add-ons for single allowances (for example, more assets). The 30-day trial is a licence too, issued to the install when you start it. Without a licence, or once it has lapsed, the install runs as Vista Platform Core: nothing stops, nothing is deleted and every Core capability keeps working, at the Core allowance. See Editions and allowances.

    Every install runs the same images, so a licence works on any install. Four ways to get one onto an install, in the order you will usually meet them:

    How When
    Start the trial on the console A new install; no paste, no file
    Mount the token in the chart's Secret (or LICENSE_TOKEN on Docker Compose) A purchased licence, kept in your deployment configuration
    Paste the token on Settings → License & Usage A purchased licence, a renewal, an exception, or an air-gapped install
    Daily refresh from the licensing service Renewals arrive on their own while the install can reach the service

    These can all be present at once. The install verifies each against the keys built into the release and uses the one that expires latest: a pasted renewal, a refreshed token and a mounted Secret all work, and none can shorten a licence another grants.

    What each edition's licence does¶

    Starter, Pro Enterprise MSP
    Capabilities Every capability Every capability Every capability the platform has
    Capacity The edition's allowance (sensors, device agents, assets), plus any exceptions on the licence Unlimited, or the band agreed Per your plans
    Tenants One Many Per your plans
    Who gets what The install; one tenant All tenants get everything, unless a platform admin switches a capability off for one tenant Your plans decide: a tenant gets what its plan includes, plus any per-tenant exception
    Bound to one install Optional Optional Always

    When the licence stops granting, the install drops to the Core allowance.

    Your install id¶

    A trial is issued for one install, and an MSP licence is too. Every install gets its own id the first time it starts, and keeps it. The console shows it on Settings → License & Usage. Send it to Vista Security when you request or renew a licence. The admin service also logs the id it is using at every start:

    kubectl -n <namespace> logs deploy/admin-service | grep "this install's id"
# [edition] this install's id: 3f2c9a4e-8b1d-4c7e-9f60-2a5d7e1b0c93

    Where the id lives:

    • The chart keeps it in the Secret <fullname>-install (for a release named vista, vista-vistaplatform-install), generating it on the first helm install and preserving it on every helm upgrade.
    • The admin service records it in the database the first time it starts. From then on the database is authoritative. If the Secret later holds a different id, the database id stays in use (so your licence keeps working) and the admin service logs a WARNING: install id mismatch naming both ids and the fix.

    Back up the database and this Secret with your cluster. A rebuild that restores the database keeps the install's identity and its licence. A genuinely new install gets a new id, and its licence has to be re-issued. (A trial is one per installation: a rebuilt install does not get a second.)

    ArgoCD, Flux or helm template: set install.id¶

    GitOps tools render the chart with helm template, which cannot read the existing Secret — so, left to itself, every render writes a new id into it. Your licence still works (the database id wins), but the admin service warns on every start. Pin the id instead:

    # your values file
install:
  id: 3f2c9a4e-8b1d-4c7e-9f60-2a5d7e1b0c93   # the id from the log line above

    When install.id is set the chart uses it verbatim. On a brand-new GitOps install, generate a UUID yourself (uuidgen), set it before the first sync, and use that same value for the life of the install.

    Install or renew with a mounted token¶

    Store the token in the Secret the chart mounts (by default vistaplatform-license, key token; see license.* in the chart values):

    kubectl create secret generic vistaplatform-license \
  -n <namespace> \
  --from-literal=token='<licence token>' \
  --dry-run=client -o yaml | kubectl apply -f -

    On Docker Compose, set LICENSE_TOKEN in .env and run docker compose up -d.

    You do not need to restart anything. The platform re-reads the licence every ten minutes. To apply it straight away, restart the admin service:

    kubectl -n <namespace> rollout restart deployment admin-service

    Install or renew by pasting the token¶

    In the admin console, open Settings → License & Usage, paste the token file you received under Install a token file and click Install token. The console checks the token before it keeps it and shows the edition and expiry it installed, or says why the token was refused. It takes effect at once. This is the path for an air-gapped install, and the quickest way to apply a renewal or an exception. The page never shows the token itself.

    The daily refresh¶

    An install that holds a trial or a licence bound to its id asks the licensing service for its current token once a day. The request carries the install id, a timestamp and a signature made with the install's own key, and nothing about your tenants or inventory. If the service has a later token, such as a renewal, the install verifies it against the built-in keys, keeps it and applies it on the next pass. A failed refresh changes nothing: the licence you have keeps running, and the last attempt and its result are shown on License & Usage.

    Refresh licence, on that page, does the same on demand.

    The refresh is skipped for an install marked air-gapped and for a licence that opts out of the usage report; those are renewed by a re-issued token file. A Core install that never started a trial makes no call at all.

    Expiry, grace and the notices¶

    • Paid licences (Starter, Pro, Enterprise, MSP). The console and the tenant admins' banner warn 30 days before expiry. At expiry a grace of 30 days begins: everything keeps working, the banner is stronger and shows the date the grace ends. The licensing service can extend the grace while a renewal is in progress; the extension arrives on the daily refresh and is never beyond 90 days after expiry. After the grace, the install drops to the Core allowance.
    • A trial has no grace. It warns in its last seven days and drops to the Core allowance at its expiry, even if the install is offline.
    • Emails. The install emails the platform admins, once each, 30 days before a paid licence expires (seven days for a trial), when a paid licence's grace begins, and when the grace ends or a trial ends and the install drops to the Core allowance. These need email delivery configured on the install; the banners carry the same news either way.
    • Nothing is deleted, and nobody is locked out. After a drop, install a licence and everything is restored within ten minutes: held assets with their history, and paused agents. What stays active in the meantime is described in Starting your trial.

    The licensing service and the air-gapped switch¶

    Where an install obtains a trial, refreshes its licence and sends its usage reports is set on Settings → License & Usage → Licensing service:

    • Licensing endpoint. The default is https://licensing.vistasecurity.io. Leave the field empty to use it. Only an https:// address is accepted. Changing the endpoint grants nothing: every token is verified against the keys built into the release, so a wrong endpoint only stops trials, refreshes and report delivery from working.
    • Air-gapped (no refresh, no reports sent). Tick it on an install that cannot reach the licensing service. It stops the daily refresh, the trial request and the sending of usage reports; you renew by pasting a re-issued token file, and download each usage report and send it yourself (see What is reported to Vista Security).

    Both changes are recorded in the platform audit log.

    Check which licence is active¶

    Settings → License & Usage shows the edition, who the licence was issued to, when it expires and how many days are left, any grace, the install id and the last refresh. The admin service also logs what it verified:

    kubectl -n <namespace> logs deploy/admin-service | grep '\[edition\]'

    A line is written at start-up and again whenever the outcome changes, not on every ten-minute check.

    • licence verified: <edition> edition for "…" (…), expires …, not bound to an install (or …, bound to install <id>) — the licence is active.
    • no entitlement token configured — running as Core — there is no token file: the licence Secret does not exist, or it exists without the key the chart mounts (token by default), and the install holds no stored token. If a licence was recorded before, the line ends (the previously recorded licence was removed).
    • token present but unusable (edition: token file LICENSE_TOKEN_FILE="…" is empty) — running as Core — the Secret and its token key exist, but the value is empty (or only whitespace).
    • token present but unusable (…) — running as Core with any other reason — the token was rejected, and the reason says why: expired, signed with the wrong key, an edition this version does not recognise, a token that must be bound to an install and is not, bound to a different install (both install ids are printed — send the one for this install to Vista Security), or bound to a different cluster than the one the install runs on.
    • WARNING: the entitlement token for "…" has no vc_edition claim — an older token. It works as an Enterprise licence for this release only; ask Vista Security for a new one.
    • this install's id: … — printed once at start-up; the id a trial or an MSP licence is issued for.
    • WARNING: install id mismatch — … — the chart's install Secret disagrees with the id recorded in the database. The database id stays in use; set install.id as the message says (see above).
    • [licence] daily refresh: … — … — the outcome of the daily refresh.

    Remove a licence¶

    Delete the licence Secret (or its token key). Within ten minutes (or after restarting the admin service) the install stops using the mounted token. A trial, refreshed or pasted token the install stored for itself is not removed by this: it stays in force until it expires. When no token is left, the install runs as Core, and the admin service logs no entitlement token configured — running as Core (the previously recorded licence was removed).
