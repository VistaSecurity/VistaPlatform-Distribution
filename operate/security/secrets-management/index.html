    Secrets Management Guide¶

    This guide covers how secrets are managed in Vista Platform, including the encryption master key for platform integrations.

    Overview¶

    The platform uses various secrets for different purposes: - Database credentials: PostgreSQL, Redis - JWT secrets: Token signing keys - Service secrets: API keys, webhook secrets - Platform integration credentials: AWS, cloud providers, SaaS integrations (encrypted)

    Docker Compose install¶

    The compose file each release attaches reads six secrets from .env and refuses to start until every one is set; none has a default. Generate them, one random value each:

    umask 077
for v in POSTGRES_PASSWORD REDIS_PASSWORD NATS_PASSWORD JWT_SECRET INTERNAL_AUTH_SECRET ENCRYPTION_MASTER_KEY; do
  echo "$v=$(openssl rand -hex 32)"; done > .env

    The services run with ENV=production, so each also refuses at startup a secret shorter than 32 bytes or one of the published development defaults (see Minimum strength). Keep .env with your backups: ENCRYPTION_MASTER_KEY encrypts the device and integration credentials you store, and a different key makes them unreadable. To rotate the others, change the value and run docker compose up -d again. The Distribution repository's INSTALL.md covers the rest of the compose install.

    Production Environment (Helm chart)¶

    Production runs the Helm chart, not a .env file — see the production checklist. The chart handles ENCRYPTION_MASTER_KEY (and the other platform secrets — JWT signing key, internal-auth HMAC secret) one of two ways:

    • Chart-generated (default). If you don't supply platform.existingSecretName, the chart generates the platform Secret on first install and keeps it — every subsequent helm upgrade reads the existing Secret back rather than regenerating it.
    • Operator-supplied (recommended for anything you'd call real). Create the Kubernetes Secret yourself, out of band, and reference it via platform.existingSecretName in values.yaml. This is what lets you source ENCRYPTION_MASTER_KEY from whatever your organization already uses — a SealedSecret, the External Secrets Operator pulling from AWS Secrets Manager or HashiCorp Vault, or a plain kubectl create secret generic against a value you generated with openssl rand -base64 32.

    Never rotate ENCRYPTION_MASTER_KEY on a live deployment. Whichever way you manage the Secret, changing its value after you have live integrations makes every credential encrypted under the old key permanently undecryptable — see Cannot Decrypt Existing Credentials below.

    Session-token signing and the legacy shared secret¶

    Session tokens are signed with ES256 (jwtSigning.enabled, on by default). The private key lives in the chart's <fullname>-jwt-signing Secret and is mounted only into the two services that issue tokens, auth-service and admin-service; every other service verifies with the public key it fetches from auth-service's JWKS endpoint.

    Before ES256, every service verified HS256 tokens with one shared secret (platform.jwtSecret, injected as JWT_SECRET). Any service holding that secret can forge a session for any user and tenant, so the migration is only finished once it is removed from the services that merely verify. That is jwtSigning.acceptLegacyHmac, and its default, auto, does it for you on install and upgrade:

    Situation Legacy HS256 accepted?
    Fresh install No. Every session is ES256 from the first token.
    The upgrade that first switches ES256 signing on Yes — every live session is still HS256.
    Later upgrades, signing key younger than jwtSigning.legacyHmacWindowHours (192h: the 7-day refresh-token lifetime plus a day) Yes
    The first upgrade after that No. JWT_SECRET is removed from every service except the two issuers.
    jwtSigning.enabled: false Yes — HS256 is the only scheme.
    acceptLegacyHmac: true or false As set.

    The window closes at an upgrade, not on a timer: an install that is not upgraded after the window passes keeps the secret until its next helm upgrade. The install and upgrade notes print which way it went and why.

    auth-service keeps JWT_SECRET regardless (it uses it for CSRF binding and for pre-cutover refresh tokens), so removing the variable is not what stops it accepting HS256. The chart sets JWT_ACCEPT_LEGACY_HMAC on auth-service from the same decision: when the window is closed it is false, and a token signed with the shared secret is refused there too. Outside the chart the variable defaults to true; it is ignored (with a warning) while no ES256 signing key is configured, since the service then signs HS256 itself.

    GitOps and helm template. auto reads the signing Secret with Helm's lookup, which returns nothing when Helm is not talking to a cluster (helm template, a client-side --dry-run, Argo CD). Rather than guess, it then keeps legacy acceptance on. If you deploy that way, set the value yourself: true while ES256 signing is younger than the window, false after.

    --reuse-values carries the previous release's chart defaults forward, so an upgrade with it from a chart that defaulted to true stays true. Use --reset-then-reuse-values across chart versions.

    To confirm the result on a service that only verifies:

    kubectl -n <namespace> get deploy inventory-service \
  -o jsonpath='{.spec.template.spec.containers[0].env[*].name}' | tr ' ' '\n' | grep JWT_SECRET

    No output means the legacy secret is gone from it. Check that the pods actually restarted rather than trusting a green helm upgrade — environment variables are read at pod start.

    Minimum strength (enforced at startup)¶

    When ENV=production (the chart's default, appConfig.env), every service checks its platform secrets before it serves, and stops with a message naming the variable if one is wrong:

    Variable Production rule
    INTERNAL_AUTH_SECRET Required, at least 32 bytes
    ENCRYPTION_MASTER_KEY Required, at least 32 bytes. An absent key is refused rather than run with credential encryption off
    JWT_SECRET If set, at least 32 bytes. May be absent on services that only verify tokens once ES256 verification is configured and legacy HS256 is no longer accepted (jwtSigning.acceptLegacyHmac resolves to false — see Session-token signing); auth-service and admin-service still require it

    The published development defaults are refused as before. Anything generated by the chart or by openssl rand -hex 32 (64 bytes) or openssl rand -base64 32 (44 bytes) passes. Outside production the same problems are logged as warnings and the service keeps running; a service that stores credentials also reports "credential_encryption": "disabled" in its /health payload while ENCRYPTION_MASTER_KEY is unset.

    Upgrading an install that supplied its own short secret. The new pods exit at startup with a line such as refusing to start in production: INTERNAL_AUTH_SECRET is 12 bytes; production requires at least 32, so a rolling upgrade stops with the old pods still serving. Replace the value in your platform Secret (platform.existingSecretName, or platform.* values), then re-run the upgrade:

    • INTERNAL_AUTH_SECRET: set a new random value. Services restart together; it is only used to sign calls between them.
    • JWT_SECRET: set a new random value, or remove it from verifier services once ES256 is on. Existing legacy HS256 sessions are invalidated.
    • ENCRYPTION_MASTER_KEY: there is no in-place re-key. The data key is derived from the exact string, so a new key cannot read credentials stored under the old one. Set the new key, then re-enter the integration, device and connector credentials you want to keep (they were encrypted under the old key and will report as undecryptable until replaced).

    Platform Integration Credentials¶

    How Encryption Works¶

    When a platform admin creates an AWS integration:

    1. User enters credentials in the admin UI (plaintext)
    2. Frontend sends to backend API
    3. Backend encrypts sensitive fields (access_key_id, secret_access_key, etc.) using ENCRYPTION_MASTER_KEY
    4. Encrypted credentials are stored in platform_integrations.config (JSONB column)
    5. When retrieved, credentials are automatically decrypted

    Encryption Details¶

    • Algorithm: AES-256-GCM (authenticated encryption)
    • Key Derivation: HKDF-SHA256 from ENCRYPTION_MASTER_KEY (format v2)
    • Nonce: Random for each encryption operation
    • Sensitive Fields: access_key_id, secret_access_key, session_token, api_token, api_key, password, client_secret

    Security Features¶

    • Encrypted at rest: All credentials stored encrypted in database
    • RBAC protected: Only platform admins with platform.settings permission can access
    • Audit logging: All credential changes logged to platform_integration_audit_log
    • No plaintext storage: Credentials never stored in plaintext

    Sourcing the key from a key management service¶

    The platform reads ENCRYPTION_MASTER_KEY from its Secret; it does not call a key management service itself. To keep the key in AWS Secrets Manager, HashiCorp Vault, Azure Key Vault or similar, have that system deliver the value into the Secret the chart reads (platform.existingSecretName), for example with the External Secrets Operator, as described under Production Environment. The value must then never change: there is no re-keying of stored credentials (see Cannot Decrypt Existing Credentials).

    Troubleshooting¶

    "Platform integration management will be disabled" Warning¶

    Problem: ENCRYPTION_MASTER_KEY is not set.

    Solution: 1. Docker Compose: set ENCRYPTION_MASTER_KEY in .env (see Docker Compose install) 2. Helm: verify platform.existingSecretName (or the chart-generated Secret) actually contains encryption-master-key 3. Restart the admin-service pod/container

    "Failed to encrypt config" Error¶

    Problem: Encryption service failed to initialize.

    Possible Causes: - ENCRYPTION_MASTER_KEY is empty - Key derivation failed - Key management service unavailable

    Solution: 1. Verify ENCRYPTION_MASTER_KEY is set and not empty 2. Check service logs for detailed error messages 3. Verify key management service is accessible (if using one)

    Cannot Decrypt Existing Credentials¶

    Problem: Error decrypting credentials after key change.

    Cause: The encryption master key was changed, but existing credentials were encrypted with the old key.

    Solution: - DO NOT change the encryption key if you have existing integrations - If you must change the key: set the new key, then re-enter every integration, device and connector credential you want to keep (each reports as undecryptable until replaced). There is no in-place re-key.

    Prevention: keep the key with your backups, and deliver it from a secrets manager through platform.existingSecretName so it never changes by accident.

    Client address behind a proxy (auth-service)¶

    auth-service keys its per-address sign-in and registration limits on the caller's address, and writes it to audit rows and impersonation tokens. It takes that address from the TCP connection, and reads X-Forwarded-For only when the connection comes from a peer listed in TRUSTED_PROXY_CIDRS (comma-separated IPs or CIDRs); it then uses the first address in the header that is not itself a trusted proxy. With the variable unset it trusts no one.

    The chart sets it from trustedProxyCIDRs, which defaults to the private address ranges (where an in-cluster ingress controller lives). Narrow it to your ingress controller's pod CIDR if you can. Setting it to an empty list trusts nobody, so every request appears to come from the ingress controller and the per-address limits share one bucket. A Docker Compose install does not set it, with the same effect.

    Failed sign-ins are counted per account and client address, and only failures count: signing in correctly never moves an account toward a lockout, and a stranger's failures from their own address cannot lock the owner out. When a lockout expires the account's failure count starts again from zero, so one typo afterwards does not lock it a second time.

    Deactivating or deleting a user, resetting or changing a password, and revoking a session each write a per-user "tokens issued before this moment are invalid" entry to Redis, which every service's JWT middleware consults. It expires on its own once every older access token has (JWT_EXPIRY plus a few minutes). Because the check needs Redis, a service without REDIS_URL skips it and the token stays valid until it expires; every service that verifies tokens is deployed with Redis by the chart and by a release's compose.yaml. If Redis is unreachable the check fails open.
